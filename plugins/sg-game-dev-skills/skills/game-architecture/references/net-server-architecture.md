# 伺服器架構（Server Architecture）

權威伺服器這一側怎麼組織：模擬迴圈、房間制、狀態與持久化、可見性過濾。原則：**從單行程多房間開始，量級到了再分散**——過早分散式是小團隊多人專案的第一死因。

## 模擬迴圈：伺服器也有幀預算

```
固定 tick（常見 15-60Hz，動作類 30Hz 起）:
1. 收輸入      排入各玩家的輸入佇列（帶序號，見 net-prediction 的和解）
2. 模擬一步    用固定 dt 跑 gameplay（與客戶端同一套邏輯——共用模擬層）
3. 產出快照    對每個連線生成其視野內的狀態（delta 壓縮，見 data-network-sync）
4. 下發        按各自通道發送
```

- **tick rate 是成本 × 體感的旋鈕**：30Hz 動作遊戲夠用（客戶端插值補平滑）；格鬥/競技 FPS 才需要 60+。tick 翻倍 = CPU 與頻寬近乎翻倍。
- **共用模擬層**：客戶端預測與伺服器權威跑同一份 gameplay 程式碼——兩份實作的漂移沒完沒了。這要求模擬層無渲染依賴（headless 可跑，見 `system-ui.md` 的解耦測試一——在這裡兌現）。
- **tick 超時就是伺服器掉幀**：單 tick 超過預算（33ms @30Hz）要進監控與日誌（`../../game-tooling/references/perf-measurement-first.md` 的幀預算思維原封不動搬過來；效能異常埋點見 debug-logging）。

## 房間制：絕大多數遊戲的正解

```
                 ┌─ Gateway（連線接入、驗證、路由）
客戶端 ──────────┤
                 ├─ Matchmaker（配對、開房、選址）
                 │
                 └─ Room Instances（每房一個模擬實例）
                        └─ 戰局結束 → 結算上報 → 回收
```

- **一個房間 = 一個獨立模擬**：單執行緒跑一房的模擬（避開並發地獄），一個行程跑多房、一台機器跑多行程——水平擴展靠「多開房間」，不靠「一個模擬多執行緒」。
- **房間生命週期**：開房（配對成局）→ 載入（雙端就緒握手）→ 進行 → 結算（**上報中央服務**）→ 回收。結算是關鍵事務：獎勵發放走冪等（房間崩潰重試不重發）。
- **房間外的服務**（帳號、背包、商店、排行）是一般的 Req/Resp 服務（見 `net-protocol-and-connection.md` 的訊息分類）——別把它們塞進房間模擬；兩者的擴展模式完全不同。
- 大廳/城鎮這種「大量玩家低互動」空間：本質更接近聊天室 + 位置廣播，不需要戰鬥級 tick——降頻另做，別用戰鬥房的規格養。

## 狀態與持久化

- **房間內狀態活在記憶體**：戰局中不落庫——tick 內同步寫資料庫是效能自殺。
- **持久化的時機**：進房時載入（玩家資料快照進房）、結算時寫回、途中僅關鍵檢查點（見 `system-foundation.md` 的存檔 capture/restore——同一套介面，寫的目標從磁碟換成資料庫）。
- **崩潰的賠付策略**要先決定：房間炸了，戰局作廢退還入場券？還是從檢查點恢復？——多數遊戲選前者（誠實 + 便宜），MMO 級才做後者。作廢也要有事務紀錄（誰在局裡、進行到哪），客服才有依據。

## 可見性過濾（Interest Management / AOI）

每個連線只收「它該看到的」：

- **房間制通常全量**：8-16 人的房間，全同步塞得下——別為不需要的規模寫 AOI。
- **要做再做**：大世界/大逃殺（50+ 實體）用網格 AOI（空間分割直接複用 `algo-data-structures.md` 的 grid/spatial hash）——實體進出視野時發 spawn/despawn 事件，客戶端據此建立銷毀本地代理。
- **AOI 兼防作弊**：不下發的資訊無從作弊（wallhack 無物可看，承 protocol 篇的安全基線）——競技遊戲的視野過濾值得比「效能需要」更激進。

## 部署與運維的最小集

- **量級路徑**：單行程多房 → 單機多行程 → 多機（配對服務選址）——每一步都等量級逼你再走，路徑上的每一站都是可停留的終點。
- **監控三件套**：tick 耗時分佈、房間數/玩家數、異常率（斷線率、和解率）——上線後的「伺服器卡」全靠這些定位（遙測思維見 `../../game-tooling/references/telemetry-event-design.md`，伺服器是另一個埋點面）。
- **灰度與回滾**：新版本先開少量房間驗證——伺服器的 release 紀律承 `../../game-production/references/build-release-checklist.md`。

## 常見陷阱

- **過早分散式**：第一版就微服務 + 訊息佇列 + 多區部署——單行程多房能撐到你上線後很久。複雜度等需求來敲門。
- **模擬層兩套實作**：客戶端 C# 一套、伺服器另一套——預測永遠對不上權威，和解率爆表。共用模擬層是硬要求。
- **房間裡做 I/O**：tick 內查資料庫、寫日誌檔——模擬迴圈裡只有記憶體操作，I/O 全部非同步出去（見 foundation 的存檔背景寫入，同一原則）。
- **結算不冪等**：房間結算重試發了兩次獎勵——經濟事故。冪等鍵（局 id）是結算事務的標配。
- **沒有壓測就上線**：一房 16 人 × 100 房的 tick 耗時，上線前用機器人壓出來（機器人 = AI 產 intent 的另一個用途，見 `system-game-ai.md` 的 intent 共用）。
