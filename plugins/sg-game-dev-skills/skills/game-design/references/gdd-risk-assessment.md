# 風險評估（遊戲企畫特有）

one-pager 的「最大風險」欄常被寫成空話（「可能做不完」）。這篇幫你把風險寫得可驗證、可行動。

## 遊戲企畫的四類風險

### 1. 樂趣風險（最重要，最常被忽略）

「核心循環可能根本不好玩。」

- **徵兆**：企畫只在紙上成立、賣點是「組合」而非「體驗」（例：「roguelike + 種田」說不出哪個瞬間好玩）。
- **驗證方式**：最短路徑做出可玩的 core loop 原型（白盒、方塊人都行），給自己以外的人玩 10 分鐘。
- **判準先寫好**：玩測前先寫下「如果好玩，玩家會______」（會再玩一次？會問還有沒有下一關？），避免事後合理化。

### 2. 技術風險

「關鍵技術可能做不到或成本過高。」

- **徵兆**：企畫依賴一個你沒做過的技術點（大量單位同屏、程序生成、網路同步）。
- **驗證方式**：獨立的技術 spike——只驗證該點，不接遊戲本體，給自己一個時限（例：三天內 5000 單位跑 60fps，做不到就改設計）。

### 3. 範圍風險

「內容量與工期不成比例。」

- **徵兆**：企畫需要大量手工內容（幾十關、大量美術）、或「每個系統都要互相影響」。
- **驗證方式**：做 1 個代表性單位（一關、一個完整敵人），實測工時 × 數量，對照可用工期。見 `gdd-scope-cutting.md`。

### 4. 市場／受眾風險

「做得出來、也好玩，但沒人要。」

- **徵兆**：說不出目標玩家現在在玩什麼遊戲、賣點截圖無法一眼看懂。
- **驗證方式**：用一張 mockup 截圖 + 一句話描述測試反應；找 3 個目標受眾問「你會點進去看嗎？為什麼？」。

## 怎麼寫進 one-pager

「最大風險」欄的格式建議：

```
風險：<哪一類 + 具體描述>
驗證：<用什麼最小實驗確認，時限多久>
判準：<事先寫好的成功/失敗標準>
失敗時：<改設計的方向 or 放棄條件>
```

範例：

```
風險：樂趣風險——「吸收敵人能力」的循環可能只有前 3 次新鮮。
驗證：兩週白盒原型，8 種可吸收能力，找 3 人各玩 20 分鐘。
判準：至少 2 人主動玩超過 20 分鐘且能說出最喜歡的能力組合。
失敗時：改為「能力合成」方向；若仍無感，這個核心放棄。
```

## 驗證的優先順序

一次只驗一個風險，順序 = **殺傷力 × 不確定性**：

1. 先驗「失敗會讓整個企畫作廢」的（通常是樂趣風險或關鍵技術風險）。
2. 再驗「失敗要大改但不致死」的。
3. 「失敗只是變小變醜」的風險（多數範圍風險）不用原型驗，用 `gdd-scope-cutting.md` 的砍法處理即可。

## 常見陷阱

- **把風險寫成擔憂**：「怕做不完」不可行動；「第 3 章需要 40 關，以目前每關 2 天的速度需 80 天，工期只有 60 天」才是風險。
- **原型做太好**：驗證樂趣的原型加了美術和音效，好玩時分不清是玩法好玩還是包裝討喜。驗證期刻意醜。
- **判準事後補**：玩測完才決定「這樣算成功」，人會自我說服。判準先寫、寫死。
- **驗證通過就不再看**：風險欄跟範圍欄一樣，每個里程碑重讀一次——新的風險會長出來。
