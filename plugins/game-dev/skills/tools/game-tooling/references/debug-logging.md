# 日誌策略

Debug draw 服務「正在看的 bug」，日誌服務「已經跑掉的 bug」。無法重現的問題，唯一的線索是屍檢報告——日誌就是為屍檢寫的，紀律決定它有沒有用。

## 分級

四級夠用，重點是**用法紀律**而不是級數：

| 級別 | 用途 | 範例 | 發佈版 |
|------|------|------|--------|
| ERROR | 不該發生、需要修 | 讀不到存檔、狀態機進入非法狀態 | 保留＋上報 |
| WARN | 可疑但可繼續 | 資料表參照 fallback、幀預算超標 | 保留 |
| INFO | 重大狀態轉換 | 進關、存檔、購買、開始戰鬥 | 保留（低量） |
| DEBUG | 開發期細節 | AI 狀態切換、技能判定細節 | 剝離 |

紀律：

- **ERROR 零容忍**：正常遊玩不該出現任何 ERROR。放任「已知無害的 ERROR」洗版，真正的錯誤就被淹沒（破窗效應）。
- **INFO 是屍檢的骨架**：玩家回報「莫名其妙壞了」時，INFO 級應該足以還原他的操作路徑（進了哪關、做了什麼大事件）。
- 按系統加 tag（`[AI]`、`[Save]`、`[Econ]`），可過濾。

## 頻率控制

每幀狂印的日誌毀掉一切——效能、可讀性、磁碟：

```
log_once(key, msg)          # 同 key 只印第一次（初始化資訊）
log_throttled(key, msg, interval = 1s)   # 同 key 最多每秒一次（迴圈內的異常）
log_on_change(key, value)   # 值變化才印（狀態追蹤）
```

**每幀迴圈裡的 log 一律用這三種**，禁止裸 log。連續變化的數值不要用日誌看，用 debug watch 面板（見 `debug-draw.md`）。

## 遊戲特有的紀錄點

建專案時照抄的埋點清單：

- [ ] **狀態轉換**：遊戲流程（選單→載入→遊玩）、AI 狀態機、任務階段——「從 X 到 Y，因為 Z」。
- [ ] **經濟事件**：獲得/花費資源（來源、數量、餘額）——平衡屍檢與刷幣 bug 追查的原料。
- [ ] **隨機種子**：每局開始 log seed——配上種子還原，「無法重現」直接降級成「可重現」（決定論見 `../../../architecture/game-architecture/references/data-network-sync.md`）。
- [ ] **玩家關鍵操作**：進關、死亡（位置＋死因）、購買、裝備變更——足以還原操作路徑。
- [ ] **載入與版本**：啟動時 log 遊戲版本、資料表版本、平台——回報 bug 時第一個要對的資訊。
- [ ] **效能異常**：單幀超過預算（如 > 33ms）時 log 當幀的系統耗時摘要，事後可定位卡頓。

## 屍檢思維

寫每條日誌前問：「三週後只看日誌，這條能幫我回答什麼問題？」

- 差：`log("takeDamage called")` ——誰打誰？多少血？剩多少？
- 好：`log("[Combat] {attacker} hit {target} for {dmg}, hp {before}->{after}")`

**帶上下文的一條，勝過不帶上下文的十條。**

崩潰處理：捕捉未處理例外 → 把最近 N 條日誌 + 狀態摘要寫入 crash 檔。玩家附上這個檔案，屍檢才有屍體。

## 常見陷阱

- **print 除錯完就刪**：追 bug 時加的 print，資訊有價值就升級成 DEBUG 級留下，沒價值才刪。反覆加刪同一批 print 是在原地打轉。
- **日誌當 debug draw 用**：空間性、連續性的狀態（座標、速度）用日誌追，可讀性是災難——那是 debug draw 與 watch 面板的工作。
- **發佈版全關**：玩家端一條日誌都沒有，回報的 bug 全靠通靈。INFO 以上保留並輪替檔案（限制大小）。
- **敏感資訊入日誌**：帳號、token、個資不落日誌——發佈版日誌會被玩家轉傳。
