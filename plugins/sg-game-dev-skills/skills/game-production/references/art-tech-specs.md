# 技術美術規格

規格數字不是拍腦袋，是**從效能預算與畫面需求反推**。這篇給你反推的方法，算出來的數字填進 content-production 的規格表。

## Texel Density（貼圖密度）

「每公尺多少貼圖像素」——同密度的物件在畫面上清晰度一致，密度亂跳的場景一眼廉價。

- **定一個基準**：例如主要遊玩距離下 512 px/m（風格化可低、寫實要高），全場景資產照這個密度分配貼圖尺寸。
- **按觀看距離分級**：貼臉的（主角、手持武器）1-2 倍基準；遠景（山、天空盒）0.25-0.5 倍——距離就是折扣率。
- **實務作法**：在引擎裡放一個棋盤格測試材質，掃過場景一眼看出密度不均的資產。

## 貼圖尺寸與圖集

- **尺寸 = 密度 × 物件實際大小**，向上取到 2 的次方——不是「大物件就 2048」。
- **圖集（atlas）規劃**：同時出現、同材質參數的小物件合圖集（UI 圖示、地表小件、同一角色的部件），減少 draw call 與材質切換（見 `../../game-tooling/references/perf-common-hotspots.md` 的渲染熱點）。
- **圖集的取捨**：合太兇 = 改一張圖重烘整個圖集、記憶體整包載入。按「更新頻率 + 同場景共現」分組，別全塞一張。
- **壓縮格式進規格**：目標平台的壓縮格式（與品質等級）一開始定好並自動化套用（匯入自動化見 `content-pipeline-setup.md`）——後期換壓縮格式 = 全部資產重匯。

## 面數與 LOD

- **面數預算從場景反推**：目標平台的每幀三角形預算（profiler 實測，見 `../../game-tooling/references/perf-measurement-first.md`）÷ 同屏最大物件數，往下分配到各資產類型——主角 : 精英 : 雜兵 : 場景件常見是 10 : 5 : 2 : 1 的量級。
- **LOD 分級**：大量出現或遠距可見的資產做 2-3 級（LOD1 約 50%、LOD2 約 25% 面數）；只在近景出現的不用浪費。
- **輪廓優先減面**：減面先保輪廓與外緣，內部細節交給法線貼圖——輪廓塌了 LOD 切換就穿幫。

## 材質與 Shader 預算

- **材質數量 = draw call 的地板**：規格裡限制「每資產材質數上限」（角色 1-2、場景件 1）——一個模型八個材質是效能與管線的雙重災難。
- **Shader 變體控制**：特殊 shader 是特權，普通資產用標準材質庫（材質球對照板見 `art-style-guide.md`）——每多一種 shader，就多一份維護與編譯成本。
- **半透明是預算大戶**：overdraw 敏感的平台（行動裝置）規格裡直接限制半透明使用場合。

## 動畫與骨架

- **骨骼數預算**：按平台與同屏數量定（大量雜兵的骨架要精簡）；影響蒙皮成本與記憶體。
- **骨架命名與層級標準化**：共用動畫的前提是骨架一致——命名規範進規格表（見 `content-asset-conventions.md`）。
- **幀率與壓縮**：動畫取樣率、曲線壓縮容差進規格，肉眼無差的壓縮省的是大頭記憶體。

## 規格的定法（總結）

1. 從 profiler 實測拿到目標平台的預算（幀時間、記憶體、draw call）。
2. 從黃金樣本拿到「這個品質」的單件成本（貼圖量、面數、材質數）。
3. 兩者相除得出同屏容量——不夠就回頭調：降規格、減同屏數、或砍風格複雜度。
4. 寫進規格表，驗收腳本照表把關。

## 常見陷阱

- **規格抄別的遊戲**：人家的平台、鏡頭距離、同屏數量都不同。抄流程可以，數字要自己算。
- **只給上限不給基準**：「貼圖最大 2048」的結果是全部 2048。給的是 texel density 基準，上限只是保險。
- **後期才管記憶體**：貼圖記憶體是遊戲記憶體的大頭，超標時已經幾百張圖進庫了。規格第一天就含壓縮與尺寸，每週 build 看記憶體趨勢（見 `build-automation.md`）。
- **技術規格與風格脫節**：風格要柔和漸層卻用了激進壓縮（色帶災難）——規格定案前拿黃金樣本全流程走一遍（做 → 壓縮 → 進引擎 → 目標機看）。
