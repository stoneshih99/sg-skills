# 發佈流程

發版的品質不是靠最後一週的爆肝，是靠流程紀律：凍結 → 回歸 → 提交 → 監控。demo、平台上架、版本更新都是同一套，只是規模不同。

## RC 凍結（Release Candidate）

- **切 release 分支，宣告凍結**：從 main 切出（見 `build-version-control.md` 的分支策略），此後**只收 bug 修復**，不收功能、不收「順手改一下」——RC 後每個改動都要重跑驗證，改一行也一樣（見 `milestone-stage-definitions.md` 的 Gold 階段）。
- **bug 分級收斂**：blocker（不修不能發）/ major（盡力修）/ minor（記入已知問題，下版修）。發版前的爭論只剩「這是不是 blocker」一題。
- **修復回灌**：release 分支上的修復要合回 main，否則下版舊 bug 復活。

## 回歸清單（Regression Checklist）

RC build 逐項人工過一遍（自動化煙霧測試之上的人工層）：

- [ ] **全流程通關**：從新存檔玩到主要結局（或 demo 全程）——用正常速度玩，不用作弊跳。
- [ ] **存讀檔**：新檔、覆蓋、讀檔、升版舊檔相容（拿上一版的存檔來讀）。
- [ ] **設定項**：解析度/全螢幕切換、音量、按鍵重綁、語言切換。
- [ ] **中斷情境**：切後台/最小化、拔手把、斷線（若有網路）、機器睡眠喚醒。
- [ ] **邊界機器**：最低規格裝置實測（幀率、記憶體、載入時間，見 profiling 的目標裝置）。
- [ ] **除錯殘留檢查**：作弊選單、debug draw、測試關卡入口都已剝離（見 `../../../tools/game-tooling/references/debug-console-and-cheats.md` 的發佈版上鎖）。
- [ ] **法務與素材**：版權聲明、授權字型/音源清單、隱私政策連結（有遙測必備，見 `../../../tools/game-tooling/references/telemetry-event-design.md` 的合規）。

清單進版控，每次發版複用並增補——每個曾經漏掉的災難，都變成清單上的一行。

## 平台提交

- **提前讀提交規範**：各平台的審核要求（年齡分級、成就、退出行為、平台特定 UI 規範）在 beta 期就對照，不要提交前一週才發現要改架構。
- **商店素材與 build 同步準備**：截圖、預告、描述文字也在回歸期定稿——它們就是 `../../../planning/game-design/references/gdd-positioning.md` 那句定位的落地。
- **預留審核輪次**：首次提交被退件是常態，時程上排 1-2 輪重審的緩衝。

## Day-1 與上線監控

- **Day-1 patch 清單**：RC 凍結後修好但沒趕上提交的修復，整理成上線日補丁；清單在 Gold 驗收時關閉（見 milestone-review）。
- **上線日監控**：崩潰率儀表板（見 telemetry）、商店評論、社群回報通道——上線 48 小時是問題密度最高的窗口，排人（或排自己的時間）盯。
- **回報模板**：玩家回報 bug 的固定格式（版本號、平台、重現步驟、crash 檔位置）——版本號顯示在主選單就是為了這一刻。

## Hotfix 紀律

上線後炸了急修，最容易把事情弄更糟的時刻：

1. **重現 → 修復 → 在 release 分支驗證**：再急也走完煙霧測試——hotfix 引入新 bug 是經典二次災難。
2. **一次修一件事**：hotfix 不夾帶「順便」。
3. **回灌 main**，並在回歸清單補一行這個 bug 的檢查項。

## 常見陷阱

- **凍結形同虛設**：「這個功能很小，塞進去吧」——RC 後塞功能是發版延期的第一大原因。
- **回歸只測新東西**：改 A 炸 B 是常態，清單的意義就是每次全過。
- **升版不測舊存檔**：更新上線後老玩家存檔全毀，是評論區一星的最快來源。
- **發完就放假**：上線 48 小時無人監控，小問題滾成公關事件。發版日不是結束，是監控期的開始。
