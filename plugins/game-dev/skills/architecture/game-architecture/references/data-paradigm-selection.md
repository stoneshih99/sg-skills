# 範式選型（Paradigm Selection）

「這個系統該用物件導向的領域模型，還是資料驅動？」——這是架構期最常見也最常被跳過的問題。跳過的結果是慣性決定範式（工程師寫熟什麼就用什麼），而不是問題性質決定範式。這篇是裁決框架。

## 三種範式

| 範式 | 核心信念 | 擅長 | 典型場景 |
|------|---------|------|---------|
| **領域模型**（OOP / DDD 風） | 實體攜帶行為，規則封裝在物件裡 | **規則複雜度高**：實體間互動豐富、規則常變且彼此糾纏 | 戰鬥實體互動、傷害/Buff 規則裁決、物理互動、複雜 AI 決策 |
| **資料驅動** | 資料層優先，程式是解譯器（見 `data-config-driven.md`、`data-separation.md`） | **內容複雜度高**：同型內容大量擴充、流程編排、簡單資料管理 | 任務/道具/關卡表、教學與技能流程、背包/商店/信箱/排行榜 |
| **用例原型** | 先把這個玩法直寫出來，驗證了再說 | **快速驗證**：不確定好不好玩之前，架構是浪費 | Game jam、核心機制原型（見 `../../../planning/game-design/references/gdd-risk-assessment.md` 的樂趣驗證） |

關鍵區分：**規則複雜 vs 內容複雜是兩種不同的複雜**。傷害公式牽動十個系統是規則複雜（領域模型的主場）；三百個任務長得都一樣只是參數不同是內容複雜（資料驅動的主場）。把兩者混為一談，就會拿錯工具。

## 選型訊號表

兩種都能做的系統（多數系統都是），用訊號裁決：

| 訊號 | 偏向領域模型 | 偏向資料驅動 |
|------|-------------|-------------|
| 實體互動 | 多實體交叉規則（攻擊者 × 防禦者 × buff × 環境） | 多為 CRUD + 顯示，跨實體規則少 |
| 擴充的形狀 | 加的是**新規則**（新的互動方式） | 加的是**新內容**（同規則的新一列） |
| 誰在改 | 工程師改邏輯 | 設計師調表、可能開放 mod |
| 變化頻率 | 規則穩定、偶爾深改 | 內容天天加、參數天天調 |
| 序列化/同步需求 | 低（或可接受轉換層） | 高——純資料直接序列化（見 `data-network-sync.md`） |
| 批次效能 | 少量複雜物件 | 大量同型資料（見 `data-oriented-layout.md`） |

**同一系統兩種都成立的例子**（證明這是取捨不是對錯）：

- Actor 繼承階層（領域）↔ ECS 元件組合（資料，見 `data-ecs-pattern.md`）
- Buff 物件封裝規則（領域）↔ tag + effect 資料條目過通用管線（資料，見 `system-skill.md`——那篇選了資料側，理由就是本表的「擴充形狀」與「誰在改」）

## 混用策略：多數專案的真實答案

單一範式的專案很少見，**混用有章法**才是重點：

1. **巨觀一致**：無論內部什麼範式，所有模組走同一套生命週期與註冊框架（見 `system-foundation.md`）——範式自由是模組內部的自由。
2. **核心規則用領域**：規則複雜度高的地方（戰鬥裁決、經濟規則核心）用領域模型——把糾纏的規則關進物件裡，別攤平成散落各處的表查詢。
3. **內容、流程、管理用資料**：可擴充內容、流程編排、簡單管理一律資料驅動——這是量的主體。
4. **接縫的三種模式**：
   - **實體即資料**：領域實體的欄位保持序列化友善（id 參照、平坦欄位，見 `data-separation.md`）——實體同時當資料用，不需要獨立資料層。**這是預設**。
   - **流程 + 領域**：資料驅動的流程編排順序，領域邏輯處理每步規則——技能系統的標準解（時間軸驅動 cast→apply，傷害管線算規則，見 `system-skill.md` 與 `system-action-combat.md`）。
   - **資料 / 領域雙層 + bake**：編輯期表示與執行期表示真的分歧時（視覺化節點編輯器 → 編譯後資產）才建雙層，用烘焙步驟橋接——**成本最高，最後才選**。
5. **應用層當橋**：不同範式的模組之間由應用層（指令、事件，見 system-foundation 的事件通道與 `system-ui.md` 的指令回流）銜接，不要讓領域物件直接抓資料表、也不要讓資料層回呼領域內部。

## 原型的紀律

用例原型是合法範式，但有一條鐵律：**原型的產出是答案，不是程式碼**（見 `../../../workflow/game-production/references/milestone-stage-definitions.md` 的殘酷規則）。

- 原型期：直寫、硬編碼、單檔案都可以——目標是最快回答「好不好玩」。
- 驗證通過後：**按上面的訊號表重新選型再實作**，原型碼當 spec 讀，不當基底改。
- 判斷「原型碼正在長成正式版」的訊號：開始給原型加存檔、加設定表、加第二種敵人——停下來，先選型。

## 常見陷阱

- **教條化單一範式**：「我們是 OOP 專案」的下場是三百個任務各一個 class（內容地獄）；「一切皆資料」的下場是傷害規則攤平成十張表互相查（規則義大利麵）。範式跟著子系統的問題性質走。
- **範式跟人走**：誰接手就改成誰熟的寫法——選型結論寫進架構文件（一張表：子系統 × 範式 × 理由），讓決策比人穩定。
- **過早雙層 + bake**：還沒有視覺化編輯需求就建編輯期/執行期雙表示，維護兩套 schema 加一條烘焙管線——實體即資料能撐很久，撐不住再升級。
- **用資料驅動逃避規則設計**：規則想不清楚，就先做成「表 + 一堆特例欄位」——表越來越寬、解譯器 if 越來越多，這是把領域問題硬塞進資料範式的味道（見 data-config-driven 的邏輯洩漏警告，同一個病的兩個方向）。
