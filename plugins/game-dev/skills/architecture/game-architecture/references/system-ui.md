# UI 架構（UI System）

UI 的**程式組織**：畫面管理、資料流、模式選型。UX 層（HUD 內容、互動手感、無障礙、解析度與效能規格）見 `../../../workflow/game-production/` 的 UI/UX 域——這篇解決的是「第 30 個介面進來時，程式還站不站得住」。

## 畫面管理器：堆疊 + 層級

UI 的第一個架構件不是任何 pattern，是**畫面管理器（Screen Manager）**：

```
screen_manager:
    layers:                        # 層級表全專案一張（見 ui-tech-specs 的彈窗管理）
        hud        # 常駐
        screen     # 全螢幕頁（主選單、背包）——堆疊管理
        popup      # 彈窗——堆疊管理
        system     # 系統級（斷線提示、權限彈窗）——永遠最上

    push(screen)   # 開新頁：上一頁 on_hide（暫停但保留狀態）
    pop()          # 返回：還原上一頁 on_show——「怎麼進就怎麼出」免費獲得
    swap(screen)   # 換頁不留返回（主選單 → 遊戲中）
```

- **堆疊天然解決返回鏈**：Esc/B 一路 pop 到底（`../../../workflow/game-production/references/ui-hud-and-menus.md` 的進出對稱，在架構層就是一個 stack）；畫面流程圖（`../../../diagram/game-diagrams/references/game-flow-diagram.md`）的每條邊對應 push/pop/swap 之一——圖能畫出來，程式就寫得出來。
- **生命週期四段**：`load（建立，可非同步）→ on_show → on_hide → unload（銷毀）`。關鍵決策：**hide 保留狀態、unload 才釋放**——高頻頁（背包）hide 就好，重型低頻頁（圖鑑）unload 省記憶體。哪些頁走哪種策略是資料（頁面註冊表），不是各頁自己決定。
- **modal 的輸入攔截**：popup 層存在時，下層畫面停止接收輸入——在管理器統一做（輸入路由按層過濾），不是每頁自己判斷「有沒有彈窗蓋著我」。

## 模式選型：不是全專案一種

| 模式 | 資料流 | 適合 | 成本 |
|------|--------|------|------|
| **直接式**（view 腳本自己拉資料） | View 主動讀 | 一次性簡單頁（設定、確認框） | 零抽象，但邏輯長在 view 裡 |
| **MVP / Presenter** | View ↔ Presenter ↔ Model | 有互動邏輯的頁（商店的買賣流程） | 每頁多一個類，可單測邏輯 |
| **MVVM / 資料綁定** | Model → ViewModel → View（宣告式） | 資料密集、高頻更新（背包、排行、HUD 數值） | 需要綁定基礎設施 |

**實務準則**：

- 別為了一致性全上 MVVM——確認框用綁定框架是拿大炮打蚊子；也別全用直接式——背包頁的手寫刷新邏輯會長成沼澤。**按頁面的資料密度選**。
- 沒有現成綁定框架時，最小可用的替身是「**事件 + 髒標記**」：資料變更發事件 → view 標髒 → 下次顯示前重繪（見 `../../../workflow/game-production/references/ui-tech-specs.md` 的 dirty flag）——80% 的綁定收益，20% 的複雜度。

## 資料流：單向 + 指令回流

UI 與遊戲狀態的關係，照決策與執行分離（`data-separation.md`）：

```
遊戲狀態 ──(事件/快照)──► ViewModel ──► View 顯示
    ▲                                      │
    └──────(Command：BuyItem(id, n))◄──────┘ 玩家操作
```

- **UI 讀的是投影，不是本體**：ViewModel 是為顯示而生的資料形狀（背包頁要的是「排序後的清單 + 選中索引」，不是 inventory 的內部結構）——遊戲資料結構重構時 UI 不跟著炸。
- **UI 改狀態只走指令**：按鈕發 `BuyItem` 指令，經濟系統執行並發結果事件，UI 收事件更新——**UI 程式裡出現金幣扣減算式就是架構事故**。指令化的紅利：可 log（誰在什麼時候買了什麼，見 telemetry 的事件設計）、可加驗證、可回放。
- **參照用 id 不用物件**：view 持有 entity 指標，entity 死了 view 懸空——UI 只存 id，顯示時查詢（純資料原則的 UI 版）。

## 更新策略：事件驅動，不輪詢

- **預設事件驅動**：血量變了發事件，血條聽事件更新——每幀 `text = player.hp` 的輪詢是 GC 與 rebuild 的雙重罪（見 ui-tech-specs 的效能節）。
- **高頻連續值例外**：每幀都在變的（計時器、進度條）直接每幀寫，但**隔離到獨立容器**（別拖著整個 HUD 重排）且值不變不觸發重建。
- **事件風暴防護**：一次撿 30 件物品 = 30 個背包變更事件 = 30 次重繪——UI 端**合幀**（同幀多事件標髒一次，幀尾重繪一次）。這條規則放進 UI 基類，不靠每頁自律。

## 解耦驗證：兩個測試

架構好不好，用兩個思想實驗驗：

1. **砍掉全部 UI，遊戲還能跑嗎？**——headless 模式應該成立（自動化測試、伺服器模擬都靠它）。跑不了 = 遊戲邏輯長在 UI 裡。
2. **UI 整包重載，遊戲狀態受影響嗎？**——不受影響才對（UI 熱重載是迭代速度利器）。受影響 = UI 持有了本不該持有的狀態。

## 常見陷阱

- **遊戲邏輯長在 UI 腳本**：傷害計算寫在血條、購買邏輯寫在按鈕——上面兩個測試立刻死。指令回流是唯一出口。
- **view 持有 gameplay 物件參照**：懸空參照 + 序列化障礙。id + 查詢。
- **雙向綁定的循環**：view 改 viewmodel → 觸發事件 → 又寫回 view → ……宣告式綁定用單向為預設，雙向只給輸入欄位且防重入。
- **popup 各自為政**：誰都能 instantiate 彈窗、層級亂疊、輸入穿透——所有 UI 的生殺大權收在 screen manager。
- **「暫時」的直接式頁面長大**：背包從三個欄位長到五十個，刷新邏輯散在二十處——頁面複雜度升級時，遷移到 MVP/MVVM 是重構不是重寫，越晚越貴。
