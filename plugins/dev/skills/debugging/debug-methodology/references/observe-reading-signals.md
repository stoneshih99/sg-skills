# 觀察訊號：讀失敗、選觀測手段

除錯的證據來自觀察，但多數人**猜多於讀**——放著現成的 stack trace 不看就開始改。這篇是怎麼讀失敗訊號、以及 log / debugger / print 怎麼選。

## 先讀錯誤，別猜

錯誤訊息與 stack trace 是系統白紙黑字告訴你哪裡出事——**逐字讀完再假設**：

- **讀實際的訊息**：型別、訊息文字、哪個值。「大概是空指標」不如看清楚它說哪個變數是 null。
- **stack trace 的方向**：最上層通常是「炸的地方」，往下是呼叫鏈。**炸的地方 ≠ root cause**——常要沿呼叫鏈往下找「錯誤的值/狀態從哪來」（見 `process-scientific-method.md` 的 root cause vs 症狀）。
- **跳過框架雜訊**：trace 裡一大段是函式庫/框架內部，鎖定**你自己程式碼**的那幾行。
- **第一個錯誤最重要**：一連串報錯時，後面的多半是第一個的連鎖後果——從最早那個查起。
- **錯誤訊息會誤導但很少說謊**：「找不到檔案」可能真相是路徑/權限/工作目錄，但「檔案存取」這方向是對的。

## log vs debugger vs print

三種觀測手段，按情境選：

| 手段 | 適合 | 不適合 |
|------|------|--------|
| **互動式 debugger**（中斷點、單步、看變數） | 本地可重現、要逐步看狀態演變、複雜控制流 | 生產環境、時序敏感（一停就破壞時序）、跨機器/非同步 |
| **logging**（分級、結構化、留存） | 生產/偶發、跨請求跨服務、時序問題、要事後屍檢 | 快速一次性查看（架設成本高） |
| **print / 臨時輸出** | 最快的一次性探針、debugger 難搭的環境 | 留在程式裡（會變噪音/洩漏）、大量並發（洗版且改變時序） |

**心法**：能穩定重現、要看「狀態怎麼一步步變壞」→ **debugger**；偶發/生產/時序/分散式 → **log**；只想快問一句「這裡到底跑到沒、值多少」→ **print**（用完即刪）。

## 埋在哪、記什麼

觀測不是到處灑 log，是**在決策點與邊界**放：

- **邊界**：I/O、外部呼叫、模組交界——輸入輸出各記一次，快速判斷「壞在我這還是對方」。
- **決策點**：分支條件的實際值、迴圈的關鍵狀態——記「為什麼走了這條路」。
- **記 why 與上下文**：不只「進到這」，記關鍵變數值、request id，才能事後拼出時間線。
- **分級**：ERROR/WARN/INFO/DEBUG 分開，平時關 DEBUG，查問題才開——別讓噪音淹沒訊號。

## 難纏的一類：heisenbug / flaky / race

「時好時壞」「加了 log 就不出現」——通常是**時序/共享狀態**問題：

- **race condition**：多執行緒/非同步存取共享狀態，結果取決於時序。加 print 改變時序 → bug 躲起來（heisenbug）。用**事後 log（不改時序）**或 thread sanitizer / race detector，別靠中斷點。
- **flaky（時好時壞）**：找**不確定性的來源**——未初始化的值、依賴迭代順序、時間/亂數/時區、測試間殘留狀態、外部依賴。固定每一個（種子、凍時間、隔離狀態）直到穩定重現或穩定通過。
- **順序依賴**：A 單獨跑過、和 B 一起跑掛——共享的全域/檔案/DB 狀態沒隔離。
- 判準：flaky 不是「重跑就好」，是**尚未理解的不確定性**——放著它遲早在生產咬你。

## 常見坑

- **不讀 stack trace 就開改**：現成證據擺著不看——逐字讀完再假設。
- **修在炸的那行**：那是症狀點，沿呼叫鏈找錯誤狀態的來源。
- **被連鎖報錯的最後一個誤導**：從**第一個**錯誤查起。
- **對時序 bug 用中斷點**：一停就破壞時序、bug 躲起來——用不改時序的 log/detector。
- **print 忘了刪**：變噪音、可能洩漏敏感資料——用完即刪（或本來就用 log 分級）。
- **flaky 靠重跑蓋過去**：不確定性沒消失，只是延到生產爆——當成真 bug 追。
- **log 到處灑**：噪音淹訊號——埋在邊界與決策點、分級控制。
