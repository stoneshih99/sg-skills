# 優化手法選擇

定位到熱點後，手法按「風險低 → 高」排序嘗試：先做不動架構的（少做事、換時機），再做結構性的（換佈局、換演算法）。**每改一項，回去量測一次。**

## 第一層：少做事（最便宜，先試這層）

- **剔除（Culling）**：看不見的不畫、不更新——視錐剔除、距離剔除、螢幕外的 AI/動畫降級或暫停。
- **降頻**：不需要每幀的邏輯改每 N 幀跑（AI 決策 5-10Hz 就夠、UI 刷新事件驅動）。多個降頻系統**錯開相位**，避免同一幀全部醒來變成新的 spike。

```
# 分攤：每幀只更新 1/N 的實體，錯開相位
function update_ai_staggered(entities, frame):
    for i in 0..entities.count:
        if (i + frame) % N == 0:
            update_ai(entities[i])
```

- **髒標記（Dirty Flag）**：值沒變就不重算（UI 文字、排序、路徑）。「變化時標髒、用到時才算」。
- **LOD（Level of Detail）**：距離遠的用低配版——模型面數、動畫骨骼、AI 行為、物理精度都能分級。

## 第二層：換時機（把成本移出熱路徑）

- **預計算**：執行期算的改離線算（烘焙導航、查表代替三角函數/曲線）。
- **預熱**：首次使用成本移到載入期（shader、物件池預先填滿）。
- **分幀（Time-slicing）**：大工作切片，每幀做一點（尋路大量請求排隊、每幀處理 K 個；程序生成分幀鋪）。
- **非同步 / 背景執行緒**：載入、尋路、生成丟到背景，完成後回主執行緒套用。注意：跨執行緒共享狀態是 bug 溫床，用「送資料出去、收結果回來」的訊息式交接（純資料的好處，見 `../../../architecture/game-architecture/references/data-separation.md`）。

## 第三層：換結構（收益大，動刀也大）

- **物件池**：頻繁生成銷毀 → 預配置重用。池要預熱到峰值容量，否則高峰時擴池反而 spike。
- **批次**：渲染合批（instancing/圖集）、邏輯批次處理（同型資料一次掃完）。
- **資料佈局**：AoS→SoA、冷熱切分——熱迴圈快取命中率的根本解，見 `../../../architecture/game-architecture/references/data-oriented-layout.md`。
- **空間分割**：全量掃描 → grid / spatial hash / quadtree，見 `../../../architecture/game-architecture/references/algo-data-structures.md`。
- **換演算法 / 容器**：熱路徑的 O(n²) → O(n log n)；線性查找 → hash。複雜度層級的改善通常勝過所有微優化。

## 選擇心法

1. **先問「能不能不做」**（剔除/降頻/髒標記），再問「能不能晚點做/先做好」（分幀/預計算），最後才「換個做法」（結構）。
2. **量級要對症**：瓶頸 5ms 的系統做 0.05ms 的微優化沒有意義；優先攻佔比最大的。
3. **保留可讀性的底線**：為 0.1ms 把清晰程式改成魔法，維護成本會加倍奉還。優化過的區塊加註解說明「為什麼這樣寫 + 當時的量測數字」。
4. **優化是有預算的工程**：修到預算內就停手，不是修到極限。剩下的時間拿去做遊戲。

## 常見陷阱

- **跳過第一層直上結構**：還沒試剔除降頻就重寫成 SoA/多執行緒——高風險手法解決低層問題。
- **池化一切**：低頻物件池化只增加複雜度與記憶體佔用。池給「高頻生成銷毀」的東西。
- **多執行緒當萬靈丹**：加執行緒帶來同步成本與 heisenbug；先確定單執行緒的浪費清完了。
- **優化完不寫下來**：三個月後有人（包括你）把「奇怪的寫法」重構回直觀版，效能無聲退化——所以量測面板要常駐（見 `perf-measurement-first.md`），退化當天可見。
