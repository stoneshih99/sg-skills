# 基礎設施（Foundation）

模組管理、事件、計時、資源、存檔——每個系統都依賴的地基。地基的特性：**錯了以後全家跟著錯，而且最難換**（第 10 個系統上線後想改事件派發時機，等於全部重測）。所以這篇的每個決策都值得在專案第一週想清楚。

## 模組管理：顯式生命週期，不是 singleton 網

**問題**：每個系統一個 singleton，互相在建構時抓對方——初始化順序靠運氣、關閉順序沒人管、測試無法替換。

**解法**：一個**服務註冊表** + 顯式的生命週期：

```
game_root:
    modules（宣告順序即初始化順序，寫成一張表）:
        1. TimeService          # 誰都依賴的最先
        2. EventBus
        3. ResourceManager
        4. SaveSystem
        5. AudioSystem
        ...
    boot:      依序 init()（可宣告依賴，啟動時驗證順序合法）
    shutdown:  反序 shutdown()（後進先出——依賴者先關）
    get(T):    服務查詢——模組間取用的唯一入口
```

- **取用集中一個入口**：service locator 與 DI 之爭在遊戲圈的務實答案是「小專案 locator 夠用，但**取用點集中**」——散落全專案的 `XxxManager.Instance` 是隱式依賴網，改成 `services.get(T)` 至少讓依賴可搜尋、可替換（測試時換 mock）。
- **初始化順序是一張表**，不是散在各建構子——順序錯誤要在啟動時炸（斷言依賴已就緒），不是上線後偶發。
- **模組介面窄**：其他系統只該看到模組的介面，不是內部（見 `../../game-diagrams/references/system-relation-map.md` 的入邊原則——被全家依賴的東西要刻意穩定）。

## 事件系統：兩個派發時機，選錯全家順序病

**先問要不要事件**：A 呼叫 B，若 A 本來就該知道 B（戰鬥呼叫傷害管線），直呼——事件不是解耦萬靈丹，濫用事件 = 把呼叫鏈打散成沒人追得動的隱式流程。事件用在「發生者不該知道誰在聽」（擊殺事件：任務、成就、統計都在聽）。

**核心設計決策——派發時機**：

| 模式 | 行為 | 優點 | 代價 |
|------|------|------|------|
| **立即派發** | emit 當下同步呼叫所有訂閱者 | 直觀、事件鏈當幀完成 | 訂閱者回呼裡再 emit → 深層遞迴；處理順序耦合呼叫點 |
| **佇列派發** | emit 入列，幀尾（或固定階段）統一處理 | 順序可控、天然防遞迴、可 log 全部事件流 | 一幀延遲；「emit 完立刻讀結果」的寫法失效 |

**建議**：gameplay 事件走**佇列**（幀尾派發，事件是純資料所以入列零負擔——見 `data-separation.md`）；少數要求同幀反應的（命中→回饋同幀，見 `system-action-combat.md` 的 emit）標記為立即通道。兩種通道明示，不要混在一個 API 裡讓呼叫者猜。

- **訂閱綁生命週期**：訂閱時綁 owner，owner 銷毀自動退訂——忘記退訂的懸空訂閱者是「偶發 crash + 幽靈行為」之王。手動退訂靠自律，自律必失敗。
- **遞迴保險絲**：事件觸發事件的深度上限 + 超限 log（與 `system-skill.md` 的 buff 遞迴防護同一條絲）。
- **事件即遙測的上游**：gameplay 事件流本身就是 `../../game-tooling/references/telemetry-event-design.md` 埋點的天然來源——佇列派發順便給你一個可觀測的事件 log。

## 計時與排程：全遊戲一個時間服務

- **所有 dt 從 TimeService 拿**：`game_dt`（受 timescale/暫停影響）與 `real_dt`（UI/除錯用）兩軌——哪個系統吃哪軌是顯式決策（見 `../../game-tooling/references/debug-time-control.md` 的界線清單）。直接讀系統時鐘的模組會在慢動作時脫隊。
- **延遲呼叫 / 冷卻 / 週期 tick 走同一個排程器**：到期時間丟最小堆（`algo-data-structures.md` 的 heap 排程），每幀只看堆頂——每個系統自己開計時器的下場是暫停時漏掉一半。
- **排程器回呼裡的時間語意**：暫停時到期的 timer 怎麼辦（凍結順延）？timescale 0.1 時冷卻走 game 時間還是 real 時間（設計決策：多數 gameplay 冷卻走 game 時間）？——寫進排程器文件，不是每個呼叫者自己猜。

## 資源管理：handle + 引用計數

```
handle = resources.load("enemies/slime")     # 回 handle，內部 refcount +1
handle.release()                              # -1；歸零後進卸載候選（延遲卸載，防抖動）
```

- **用 handle 不用裸資源參照**：誰在用什麼一目了然、可統計、可強制卸載時知道炸到誰。
- **生命週期分域**：全域資源（UI 圖集、常用音效）常駐；**場景域資源綁場景生命週期**（換場景自動釋放該域全部）——手動配對 load/release 在場景切換時必漏，域是兜底。
- **同步/非同步的紀律**：載入畫面內同步可以，**遊玩中一律非同步**（見 `../../game-tooling/references/perf-common-hotspots.md` 的載入 spike）；非同步的回呼要處理「回來時需求已消失」（怪還沒載完就被清場）。
- **熱重載鉤子**：資料表與資產的重載入口（`data-config-driven.md` 的熱重載）在資源層留好——事後補的熱重載總是漏一半快取。

## 存檔架構：純資料 + 原子寫入 + 版本

- **存什麼**：可序列化的純資料快照（`data-separation.md` 與 `data-network-sync.md` 的序列化原則直接複用——存檔就是「寫到磁碟的快照」）。每個系統提供 `capture() → data` 與 `restore(data)`，存檔系統只做聚合。
- **原子寫入**：寫暫存檔 → 驗證 → rename 覆蓋——直接覆寫舊檔的專案，遲早收到「存檔壞了」的一星評論（斷電/崩潰在寫入中途）。保留上一份備份，損毀時降級。
- **版本號 + 遷移鏈**：檔頭帶版本，舊檔逐版遷移（v3→v4→v5）——「改個欄位讓全部老玩家存檔報廢」是 release-checklist 的必測項（見 `../../game-production/references/build-release-checklist.md` 的舊存檔相容）。
- **autosave 時機**：安全點觸發（過關、回城），不要定時器亂入戰鬥中——存檔瞬間的卡頓與狀態不一致都在最糟的時刻發生。寫入走背景執行緒，主執行緒只做快照。

## 常見陷阱

- **singleton 互抓成網**：初始化順序靠檔名運氣——服務表 + 顯式順序。
- **事件回呼裡改狀態又發事件**：立即派發下的深層遞迴與順序依賴，重構時全家崩——佇列 + 深度保險絲。
- **懸空訂閱**：關掉的介面還在聽事件、死掉的怪還在收 tick——訂閱綁 owner 生命週期。
- **遊玩中同步 load**：一顆技能圖示卡 200ms——遊玩中一律非同步 + 預載。
- **存檔直接覆寫**：原子寫入三步是底線。
- **地基「之後再改」**：事件時機、時間雙軌、資源域——這三個決策的重構成本隨系統數量平方成長，第一週定案最便宜。
