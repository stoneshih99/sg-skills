# 輸入手感

玩家說「操作遲鈍」「吃指令」，幾乎都不是延遲問題，而是**缺容錯窗口**。好的輸入手感 = 玩家的「意圖」被理解，而不是按鍵被精確執行。

## 容錯機制清單

- [ ] **Input Buffer（輸入緩衝）**：動作進行中按下的指令，暫存 100-200ms，當前動作一結束立刻執行。沒有 buffer 的遊戲，玩家必須「掐準」動作結束的那幀才能接招——這就是「吃指令」的主因。

```
on_input(action):
    buffer[action] = now
on_actionable():                     # 角色恢復可行動的那幀
    for action in buffer:
        if now - buffer[action] <= BUFFER_WINDOW:
            execute(action); clear(action)
```

- [ ] **Coyote Time（土狼時間）**：離開平台邊緣後的 50-120ms 內仍可起跳。沒有它，玩家「明明按了跳卻掉下去」，且永遠覺得是自己的錯以外的問題。
- [ ] **Jump Buffer**：落地前按跳，落地瞬間自動起跳（input buffer 的特例，平台遊戲必備）。
- [ ] **取消窗口（Cancel Window）**：動作的後搖（recovery）可被移動 / 閃避 / 下一招取消。全程不可取消的長動畫 = 「笨重」的主因。明確定義每個動作的：前搖（不可取消）→ 生效幀 → 後搖（可取消區間）。
- [ ] **邊角修正（Corner Correction）**：跳躍撞到平台邊角時自動推開幾個像素讓玩家過去；差一個像素卡住的挫折不值得保留。
- [ ] **搖桿死區與靈敏度曲線**：死區太大 = 遲鈍，太小 = 漂移。類比輸入用曲線（緩起陡尾）而非線性。
- [ ] **同幀衝突的優先序**：跳和攻擊同幀按下誰先？定義清楚並保持一致。

## 反應時間的預算

從按鍵到「玩家看得到的反應」應在 **100ms（6 幀）內**；理想是 1-3 幀內至少有視覺起始（哪怕只是前搖第一幀）。超過 100ms 玩家開始感覺「遲鈍」。

- 動畫可以有前搖，但**第一幀就要動**——前搖是反應的一部分，不是反應前的空白。
- 若機制需要蓄力 / 延遲生效，用即時的視覺回饋（蓄力特效、音效起音）填補。

## 排查法

「操作不跟手」時依序檢查：

1. 錄影逐幀數：按鍵到第一個視覺變化隔幾幀？（> 6 幀就是問題）
2. 有沒有 input buffer？窗口多長？（連招接不上 → buffer 太短或沒有）
3. 動作後搖可否取消？（感覺笨重 → 取消窗口太晚）
4. 平台遊戲：有沒有 coyote time 與 jump buffer？

## 常見陷阱

- **把容錯當作弊**：coyote time、buffer 是「理解意圖」，不是降低難度。硬派遊戲一樣需要，只是窗口較短。
- **窗口長到誤觸發**：buffer 超過 250ms，玩家早就改主意的輸入還被執行，變成「自己動」。
- **動畫優先於輸入**：為了動畫完整禁止取消，手感為動畫陪葬。動畫服務手感，不是反過來。
- **不同動作容錯不一致**：跳有 buffer、攻擊沒有，玩家會覺得「時靈時不靈」，比全都沒有更糟。
