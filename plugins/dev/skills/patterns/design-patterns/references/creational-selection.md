# 建立型選型（Creational）：new / Factory / Builder / Singleton

**預設是直接 `new`**——建立型 pattern 是「建構出了問題」的解法，不是起手式。這篇是往上加工的階梯與每一階的進場訊號。

## 階梯：痛到哪一階，用哪一階

| 階 | 進場訊號（沒有就別上） | 代價 |
|----|----------------------|------|
| **直接 new** | 預設 | 呼叫端認識具體類——通常沒問題 |
| **Factory 函式/方法** | 建構含分支邏輯、或想隱藏具體型別（回傳介面） | 多一層間接 |
| **Abstract Factory** | **整族**物件要一起切換（平台族、皮膚族、測試替身族） | 加一個產品=改所有工廠 |
| **Builder** | 參數多且有組合約束、需要分步構建後驗證 | 樣板碼多 |
| **Prototype** | 以複製代替建構——從模板實例產出變體 | 深淺複製的坑 |

- **Factory 的真實痛**：同一段「if 條件 → new 不同類」出現在第二個地方——收攏成一個函式。第一個地方出現時**還不用**（YAGNI）。
- **Abstract Factory 只有一族產品就是過度設計**——那只是個普通 factory 加了儀式。
- **Builder 的價值在不變式**：`build()` 時驗證組合合法性。只是 setter 串鏈、最後不驗證的「builder」，不如具名參數/設定物件。
- **Prototype 在遊戲圈的化身是 spawn 模板**：從資料定義的原型複製出實例——資料驅動生成的機制（遊戲落地見 **sg-game-dev-skills** 的 data-config-driven）。

## Singleton：問題不是全域，是三件別的事

Singleton 被罵不是因為「只有一個實例」，是它同時帶來：

1. **隱藏依賴**：函式簽名看不出它用了什麼——呼叫 `Foo.Instance` 的程式碼，依賴圖是謊言。
2. **生命週期失控**：誰先初始化、誰先關閉沒人管——「A 的建構子裡抓 B.Instance，B 還沒好」是經典開場。
3. **測試無法替換**：靜態抓取無縫可插——想 mock 就得全域改狀態，測試互相污染。

**替代階梯（由好到壞）**：

```
明確傳參（依賴出現在簽名上）
> 建構子注入（組裝點集中，測試換替身）
> 服務定位器（仍隱藏依賴，但至少可替換、生命週期集中）
> singleton（無狀態工具類勉強可接受；有狀態的就是技術債）
```

- 幾十個系統互相依賴的組裝問題（遊戲引擎脈絡的模組生命週期、服務表與顯式初始化順序）是另一個量級的題目——見 **sg-game-dev-skills** 的 system-foundation；Unity 的落地裁決（服務定位 vs singleton）見 **sg-unity-dev-skills** 的 script-architecture-glue。本篇只管語言中立的論證。

## 常見坑

- **第一天就開工廠**：只有一個產品、一個呼叫端——直接 new，痛了再收攏。
- **singleton 網**：singleton 抓 singleton，初始化順序靠檔案載入運氣——依賴注入或服務表。
- **factory 回傳具體類**：呼叫端還是認識實作，白加一層——factory 的意義在回傳抽象。
- **builder 無驗證**：分步構建完不檢查不變式——組合非法在使用時才炸，離案發現場很遠。
- **用繼承做物件變體**：EnemyFast、EnemyStrong、EnemyFastStrong 類爆炸——變體是資料不是型別（prototype/資料驅動）。
