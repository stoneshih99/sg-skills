# 資產規範

規範的目的只有一個：**讓任何人（含未來的你和自動化腳本）不用問就知道東西叫什麼、放哪裡、長什麼規格**。規範越晚立，改名搬家的成本越高——資產量破百前立好。

## 目錄結構

按**內容類型**分層，同一內容的所有檔案聚在一起：

```
assets/
├── characters/
│   ├── player/
│   └── enemies/
│       └── slime/            # 這隻敵人的模型/貼圖/動畫/材質全在這
├── environments/
│   └── forest/
├── ui/
├── audio/
│   ├── music/
│   └── sfx/
├── vfx/
└── _shared/                  # 跨內容共用（通用材質、共用貼圖）
```

- **聚合優於分散**：`slime/` 一夾帶走全部相關檔，勝過模型一區、貼圖一區、動畫一區——刪一隻敵人時你會感謝這個決定。
- **共用資產進 `_shared` 並嚴格把關**：什麼都丟共用，最後誰都不敢刪任何東西。
- 結構與 `content-pipeline-setup.md` 的管線步驟對齊：管線第 N 步的輸出，有固定的家。

## 命名規則

一開始就定死，全專案一致：

- **格式**：`<類型前綴>_<內容名>_<變體/部位>_<編號>`，全小寫（或全 PascalCase，擇一），禁空格與特殊字元。

```
tex_slime_body_01        # 貼圖
mat_slime_body           # 材質
mdl_slime                # 模型
anim_slime_attack_01     # 動畫
sfx_slime_hit_01         # 音效
lvl_forest_03            # 關卡
```

- **前綴讓型別可搜尋**：搜 `sfx_` 就是全部音效——自動化規則也靠前綴分流（匯入設定按前綴套用）。
- **編號留兩位**：`_01` 不是 `_1`，排序才不會 1, 10, 2。
- **禁止 `final`、`new`、`v2_real`**：版本交給版控（見 `build-version-control.md`），檔名只描述內容。

## 規格表（Spec Sheet）

每類資產一張規格表，是驗收與外包的依據（見 `content-outsourcing-handoff.md`）：

| 項目 | 範例欄位 |
|------|---------|
| 貼圖 | 尺寸上限、2 的次方、格式、命名、是否需要法線/遮罩 |
| 模型 | 面數預算（per 類型）、單位比例、原點位置、朝向、骨架命名 |
| 動畫 | 幀率、命名、根位移處理、循環點 |
| 音效 | 格式、採樣率、響度標準（LUFS）、長度上限 |
| 關卡 | 尺寸網格、出入口規格、必備標記（生成點/檢查點） |

- 規格來自**黃金樣本的實測**（樣本的面數就是面數預算的基準）+ **目標平台的效能預算**（見 `../../../tools/game-tooling/references/perf-measurement-first.md`）。
- 規格表版本化：改規格 = 新版本 + 記錄哪些既有資產需要補課。

## 驗收清單

每份資產進倉庫前過一遍（能自動化的自動化）：

- [ ] 命名符合規則（腳本可查）
- [ ] 位置正確（腳本可查）
- [ ] 規格達標：尺寸/面數/格式/響度（腳本可查）
- [ ] 進引擎顯示正常：比例、朝向、材質連結（人工抽查）
- [ ] 與黃金樣本並排無風格違和（人工）

## 常見陷阱

- **規範只存在某人腦中**：新協作者第一天就該拿到規範文件；問三次同樣問題 = 文件缺一段。
- **特例不斷**：「這個先隨便放，之後整理」——之後 = 永不。特例要嘛進規範成為新規則，要嘛當場改正。
- **規範過度設計**：三頁的命名哲學沒人讀。一頁表格 + 範例，夠用就好。
- **立了不執法**：驗收清單沒人跑，三個月後 `textures/` 裡躺著 `IMG_4032.png`。把腳本檢查掛進資產提交流程（pre-commit 或 CI，見 build-pipeline）。
