# 外包與協作交接

外包翻車的原因幾乎從不是對方能力，而是**規格不清 + 回饋太慢**。交接品質決定返工率；返工率決定外包到底省不省。

## 發包前自檢

- [ ] **黃金樣本存在**：能給對方看「就是要這個」的實體參照（見 `content-pipeline-setup.md`）。沒有樣本先做樣本，或把「做樣本」當第一個小單發。
- [ ] **規格表完整**：對方不用猜尺寸、格式、命名（見 `content-asset-conventions.md`）。
- [ ] **管線接口明確**：對方交付的東西進你管線的哪一步？交付格式是否直接可用（而不是你要再手工轉一輪）？
- [ ] **量小起步**：首單發 1-3 件試水溫，驗證規格與溝通順暢，再放量。首單就發 50 件是賭博。

## 規格包（Handoff Package）

一次交清楚，勝過來回二十封訊息。標準內容：

```
handoff/
├── brief.md            # 這批要什麼：清單、數量、期限、優先序
├── spec.md             # 硬規格：尺寸/面數/格式/命名（抄 asset-conventions）
├── style-guide/        # 風格參照：黃金樣本 + 好壞對照範例
│   ├── golden-sample.*
│   ├── do/             # 對的方向（附一句為什麼對）
│   └── dont/           # 錯的方向（附一句為什麼錯）
├── templates/          # 工作檔模板（正確的比例/骨架/場景設定起手）
└── context.md          # 遊戲背景一頁：這東西在遊戲裡怎麼用、玩家怎麼看到它
```

- **do/dont 對照是風格傳達最有效的形式**：形容詞（「卡通但不幼稚」）人人解讀不同，並排圖例無歧義。
- **context 別省**：知道「這怪物會被玩家一秒殺掉五隻」的美術，會自己把輪廓做清楚——上下文讓對方做出正確的微決策。

## 輪次與回饋紀律

- **約定輪次**：報價時就講清楚含幾輪修改（常見：草稿 → 半成品 → 成品，各一輪回饋）。無上限修改的下場是雙方都痛苦。
- **草稿階段給大方向回饋**：輪廓、比例、風格對不對——草稿期一句話能改的事，成品期要重做。**成品期才第一次回饋是交接最大罪**。
- **回饋要可執行**：「感覺不太對」不可執行；「輪廓再圓潤 20%、參考 do/ 第 2 張的肩線」可執行。附圖畫紅線最快。
- **回饋要快**：對方交了草稿等你三天，檔期就飛了。約定回饋 SLA（如 24-48 小時內）。

## 驗收與入庫

- **按驗收清單逐項過**（見 `content-asset-conventions.md`）：腳本查硬規格，人工查風格一致性——與黃金樣本並排看。
- **進引擎才算驗收完成**：在 DCC 工具裡好看不算數，進遊戲、上材質、放進實際場景看。
- **問題分類回饋**：規格不符（對方修，不計輪次）vs 方向調整（計輪次）——事先講清楚這條線，避免爭議。
- **入庫走同一條管線**：外包資產與自製資產同一套命名、位置、匯入規則——資產庫裡不該分得出誰做的。

## 多人協作的內部交接

同樣的原則縮小用於團隊內分工（企劃 → 美術 → 實裝）：

- 規格與參照同樣要有，只是形式可以輕（一頁文件 + 樣本連結）。
- **交接點明確**：「關卡白盒完成」的定義是什麼（出入口標記齊、可通關、節奏段落表填好——見 `../../game-design/`）？定義不清的交接點，就是互相等待與互相責怪的來源。
- 交接物進版控，不走即時通訊軟體傳檔（見 `build-version-control.md`）。

## 常見陷阱

- **拿沒驗證的規格發包**：自己都沒照規格做過一件，規格裡的坑由外包幫你踩，返工算誰的？
- **省略草稿輪**：「直接做成品比較快」——方向錯的成品 = 全損。
- **回饋積壓批次給**：攢了十件一次回饋，前面的問題在後面九件重複出現。
- **驗收放水**：「差一點但趕時間先收」——收了就是新標準，下一批會差兩點。規格不符就退，語氣客氣、標準不動。
