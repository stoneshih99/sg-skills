# 排程與估算

遊戲開發的估算天生不準——因為核心工作是「找到好玩」，而找到之前不知道要找多久。對策不是估得更細，是**把不確定性圈在便宜的階段**，並讓計畫有預設的退路。

## 估算方法

- **只有做過的事能被估準**：寫過三次存檔系統，第四次估得準；沒做過的機制，估的不是工時是願望。沒做過的東西先做 spike（時限盒）再估。
- **垂直切片是估算的分水嶺**：切片前的一切排程都是草稿；切片給出「單位內容實測成本」後，量產期（alpha→beta）才能認真排——`關卡數 × 單關實測成本 × 1.5`。
- **三點估算抓不確定度**：樂觀 / 最可能 / 悲觀。悲觀是樂觀的 3 倍以上時，代表這項目其實「不知道怎麼做」，先 spike 再估。
- **以週為單位**：小於一週的粒度在遊戲開發的噪音下沒有意義；大於一個月的項目要再拆。

## Buffer 紀律

- **每階段 20-30% buffer**，寫明在計畫裡。不寫明的 buffer 會被當成可用時間吃掉。
- **buffer 放階段尾，不攤平**：攤平的 buffer 隱形消失（帕金森定律：工作膨脹填滿時間）。
- **buffer 用途受限**：只能吃「估算誤差」，不能吃「新想法」。想加的東西進候選清單，里程碑驗收時再議（見 `milestone-review.md`）。

## 以驗證為節點排程

排程的骨架不是功能清單，是**風險驗證的順序**（見 `../../../planning/game-design/references/gdd-risk-assessment.md`）：

1. 列出前三大風險。
2. 每個風險安排「最早能驗掉它」的節點——通常就是 prototype 與 vertical slice 的門檻。
3. 功能開發排在其驗證節點之後：核心沒驗過就不排量產、管線沒建好就不排外包。

**反例**：先排「三個月做完所有系統」再排「第四個月玩測」——等於把所有賭注押到最貴的時候才開牌。

## 依賴與關鍵路徑

- **內容依賴管線**：量產關卡前，工具與規範要先就緒（編輯器、命名、匯入流程）——管線晚一週，量產期每人每天都在付利息。
- **美術依賴設計凍結**：機制還在變就發包美術，返工率會教你做人。外包節點放在對應設計驗收之後。
- **每週一個可玩版**：不管排程怎麼切，維持「隨時有一個能給人玩的 build」——它是進度的測謊機（見 `../../../tools/game-tooling/` 讓測試便宜）。

## 時程爆掉時的砍法

爆 20% 以上時，按這個順序處理（事先寫進計畫的「預定砍法」欄）：

1. **砍範圍，不砍品質**：先動 `../../../planning/game-design/references/gdd-scope-cutting.md` 的砍序（內容量 → 周邊系統 → 打磨層）。核心體驗的品質是最後防線。
2. **不要加人救火**：新人上手期會先讓進度更慢（Brooks 法則）；小團隊尤其如此。
3. **延期是選項，但要一次延夠**：擠牙膏式延期（每次延兩週 × 6 次）士氣殺傷最大；重估一次、延一次、buffer 重設。
4. **每次砍完更新里程碑計畫**：砍掉的東西進「續作/更新清單」，不是默默消失——這讓砍範圍在心理上可執行。

## 常見陷阱

- **用理想日排程**：一天 8 小時全在開發？會議、支援、地雷 bug 至少吃 30%。用實際產能（velocity）回推，不用日曆時間。
- **把「玩起來不錯」當里程碑**：不可判定。門檻要可觀察（見 `milestone-stage-definitions.md` 的門檻範例）。
- **量產期照切片前的想像排**：切片給的實測成本才算數；如果切片成本高於預期，正確反應是砍內容量，不是假裝量產會更快。
- **排程不含玩測與修復輪**：每個階段尾的驗證與修復至少佔該階段 20%；沒排就是預定爆炸。
