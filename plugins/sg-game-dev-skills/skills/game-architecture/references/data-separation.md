# 資料與行為分離

資料驅動設計的地基：**資料是被動的、純粹的；行為是無狀態的函式**。物件不再把資料和操作綁在一起，而是資料流過一連串系統。

## 原則

- **純資料（POD, Plain Old Data）**：只有欄位，沒有方法、沒有隱藏狀態、沒有繼承包袱。看到結構就知道它「是什麼」，不需要讀方法才知道它「會做什麼」。
- **無狀態行為**：邏輯寫成 `system(data) -> result` 的函式，自己不保存狀態，所有輸入輸出都是明確的資料。
- **單向資料流**：系統讀資料 → 算 → 寫回 / 產生新資料，順序明確，易於推理與測試。

## 與 OOP 對比

傳統 OOP 把資料和行為封裝在同一個物件：

```
# OOP：資料與行為綁在一起
class Enemy:
    field hp, position, speed
    method update(dt):        # 行為藏在物件內，狀態耦合
        this.position += this.speed * dt
        if this.hp <= 0: this.die()
```

資料導向把兩者拆開：

```
# 純資料
struct Enemy:
    hp, position, speed

# 無狀態系統：吃一批資料，批次處理
function movement_system(enemies, dt):
    for e in enemies:
        e.position += e.speed * dt

function death_system(enemies):
    for e in enemies:
        if e.hp <= 0: mark_dead(e)
```

差別不只是搬程式碼：系統能一次掃**整批**同型資料（見 `data-oriented-layout.md`），資料能直接序列化（見 `data-network-sync.md`），行為能單獨測試。

## 怎麼分離（實務準則）

- **結構裡不要放方法**——需要操作就寫成外部函式 / 系統。
- **狀態集中、行為集中**：所有 Enemy 資料放一起，所有處理 Enemy 的系統放一起。
- **用 id / 索引參照，不用物件指標**：純資料互相參照時存 id 或索引，便於序列化與重組（指標無法序列化）。
- **把「決策」與「執行」分開**：系統先算出「要做什麼」（產生指令 / 事件資料），再由另一階段執行，讓決策可記錄、可回放、可同步。

## 遊戲情境

- 大量同型單位（子彈、敵人、粒子）：分離後可批次更新，效能與可讀性雙贏。
- 需要存檔 / 回放 / 網路同步：純資料直接序列化，行為不需要跟著存。
- 團隊分工：設計師調資料、工程師寫系統，介面就是資料 schema。

## 陷阱

- **半吊子分離**：資料結構裡又偷放幾個方法或懶載入快取，純粹性一破，序列化與批次處理的好處就打折。
- **過度拆分小系統**：系統切太碎會產生大量中間資料與重複遍歷；以「一次遍歷做完一組相關運算」為粒度。
- **用指標互參**：直接存物件參照會讓序列化與重定位變困難，改存 id / 索引。
- **不是所有東西都要資料導向**：UI、一次性的高階流程用 OOP 往往更直覺；把資料導向留給「大量、同型、每幀跑」的熱路徑。
