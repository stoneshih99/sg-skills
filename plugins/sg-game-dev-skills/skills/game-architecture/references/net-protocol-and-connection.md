# 協定與連線（Protocol & Connection）

訊息怎麼設計、走什麼傳輸、斷了怎麼辦。協定層的品質決定「網路爛的玩家」的體驗下限——而玩家的網路永遠比你測試時爛。

## 傳輸：按訊息性質分通道

TCP vs UDP 不是二選一，是**每類訊息各選各的**：

| 通道 | 語意 | 用於 |
|------|------|------|
| reliable-ordered | 必達且有序（TCP 或 UDP 可靠層） | 登入、購買、聊天、關鍵事件 |
| unreliable-sequenced | 可丟、只收最新（UDP + 序號去舊） | 位置/狀態快照——**舊的到了直接扔**，重傳一個過期位置毫無意義 |
| reliable-unordered | 必達但不等順序 | 獨立事件（擊殺通報） |

- 即時動作遊戲的主體走 UDP + 自訂通道層；回合制/非同步遊戲全 TCP（或 WebSocket）完全成立——**別為不需要的即時性付 UDP 的複雜度**。
- 每則訊息在定義時就標通道——通道是訊息 schema 的一部分，不是發送時的臨時決定。

## 訊息三類：Req/Resp、Notify、高頻流

```
Req/Resp   客戶端請求 + 伺服器回應      # 帶 request_id 配對、超時、重試策略
Notify     伺服器主動推送               # 狀態變更廣播、事件通知
高頻流      輸入上行 / 快照下行          # 固定頻率、獨立通道、可丟
```

- **Req/Resp 必帶 request_id 與超時**：逾時的 UI 處理（轉圈、可重試、冪等保護）在協定層想好——「按了購買沒反應再按一次買了兩次」是協定層的鍋（冪等鍵）。
- **Notify 是事件不是狀態**：客戶端漏收一則 Notify 不能導致永久狀態錯——狀態以定期快照兜底（自我修復），Notify 只是加速感知。
- 三類分開設計、分開統計流量——混在一起的協定，出問題時連「是哪類訊息塞爆」都答不出來。

## 序列化與 Schema

基礎原則（純資料、id 參照、版本欄）承 `data-network-sync.md`，協定層再加三條：

- **Schema 單一來源**：訊息定義寫一份（IDL/表），兩端程式碼生成——手寫兩端對拷的欄位，漂移只是時間問題（與 `data-config-driven.md` 的 schema 紀律同源）。
- **量化（quantization）**：位置不需要 double——按遊戲精度量化（如 2cm 精度的定點）、角度壓到 8-16 bit、血量百分比化。高頻流的頻寬大頭在這裡省。
- **版本協商**：連線握手時交換協定版本，不相容直接拒絕並提示更新——「舊客戶端半相容地連上」產出的靈異 bug 比直接擋掉貴一百倍。

## 連線生命週期

```
握手（版本協商 + 驗證 token）
  → 進入（下發全量快照 → 切增量同步）
  → 穩態（心跳雙向、RTT 量測）
  → 異常（心跳超時 → 判斷斷線）
  → 重連（會話 token 重入 → 再走「全量快照 → 增量」）
  → 離開（優雅通知 vs 超時清理，兩條路都要有）
```

- **重連是一等公民**：行動網路下斷線是常態不是異常。會話保留時間（30-120 秒）、重連後的狀態重建（就是「進入」流程重跑）、戰局中的位置保留——第一天設計，不是上線後補。
- **心跳做兩件事**：活性偵測 + RTT/抖動量測——RTT 資料餵給預測層（`net-prediction-and-latency.md`）與 UI（延遲顯示）。
- **斷線的 gameplay 語意**要設計：暫停等人（小規模合作）？AI 接管？直接判離？——這是設計決策，寫進 GDD（見 `../../game-design/` 的規則欄），不是網路層自行發揮。

## 安全基線

- **客戶端的一切輸入不可信**：上行的是「意圖」（我要往東移動、我要買 X），不是「結果」（我在 (x,y)、我的錢 -100）——伺服器驗證並執行（與 `system-3c.md` 的 intent 分層同構，intent 天然就是上行訊息格式）。
- **不下發看不到的資訊**：牆後敵人位置不發，wallhack 就無物可看——interest management 兼防作弊（見 `net-server-architecture.md` 的 AOI）。
- **頻率限制與異常踢除**：單客戶端的訊息頻率上限、非法訊息計數踢除——協定層的基本衛生。

## 常見陷阱

- **全部走 reliable-ordered**：一個丟包塞住整條佇列（head-of-line blocking），位置更新排在聊天訊息後面——按性質分通道是協定層第一課。
- **狀態靠事件累積**：只發「+10 金幣」事件不發餘額快照，漏一則永久錯帳——事件加速、快照兜底。
- **重連 = 重新登入**：斷線 5 秒回來發現被踢出戰局——會話保留與重入流程。
- **在好網路下開發**：辦公室 1ms RTT 開發三個月，上線遇到 150ms + 5% 丟包全部露餡——**開發期常態開啟網路模擬**（延遲/抖動/丟包注入做成 debug 開關，見 `../../game-tooling/references/debug-console-and-cheats.md`）。
