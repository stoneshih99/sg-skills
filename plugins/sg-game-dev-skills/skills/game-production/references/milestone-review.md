# 里程碑驗收與回顧

里程碑的價值在驗收那一刻兌現：對照門檻、誠實判定、做出決策。沒有驗收的里程碑只是日曆裝飾。

## 驗收怎麼跑

1. **對照門檻逐條判定**：門檻在階段開始時就寫死（見範本的階段表），驗收只做三件事——展示證據、逐條打勾、記錄結果。不在驗收會上重新發明標準。
2. **證據優先**：門檻涉及玩家行為的，拿玩測資料（見 `../../game-design/`）；涉及穩定性的，拿崩潰統計；涉及完成度的，實際從頭玩一遍 build——**看投影片不算驗收**。
3. **當天出結論**：過 / 不過 / 有條件過，三選一，寫進計畫的驗收紀錄欄。

## 三種結果與決策

**過** → 進下一階段。順手做兩件事：
- 更新下一階段門檻（用這階段學到的東西校準）。
- 清一次「想加清單」：真的要加的排進下階段範圍並補時程，其他留在清單。

**不過** → 站在岔路口，選項按優先序：
1. **縮小後重驗**：砍範圍再驗一次（例：切片品質不到位 → 縮小切片範圍做到位）。給一個明確的重驗期限（2-4 週），不是無限期加班。
2. **轉向**：驗證揭示方向錯誤（prototype 不好玩、定位無人埋單）→ 回設計層改核心假設，前面的投入是學費不是沉沒成本。
3. **停案**：連續兩次重驗不過、或轉向後仍無起色。停案是合法結局——在 prototype 停案是成功的風險管理，在 beta 停案才是災難。

**有條件過**（最危險的結果）→ 只允許用於**非核心門檻**：
- 核心門檻（好玩、體驗成立）不過就是不過，「先進下一階段再補」= 把風險帶進更貴的階段。
- 條件要具體：「X 在下階段第 2 週前補齊，否則觸發重驗」，寫進紀錄，下次驗收第一條檢查。

## 回顧會（Retrospective）

驗收後 48 小時內，30-60 分鐘，三個問題：

1. **估算差在哪**：實際 vs 計畫的偏差最大的三個項目，原因是「沒做過」「範圍偷長」還是「被打斷」？——校準下階段估算。
2. **流程哪裡卡**：等資源、等決策、工具太慢？挑**一項**下階段改善（貪多不改）。
3. **範圍紀律如何**：這階段偷加了什麼？「順便做」的東西列出來（見 `../../game-design/references/gdd-scope-cutting.md` 的順便做陷阱）——不是批鬥，是讓隱形膨脹現形。

紀錄一頁以內，附在里程碑計畫後面。

## 個人開發者的特別提醒

一個人專案沒有外部驗收壓力，里程碑最容易變成裝飾。對策：

- **門檻綁外部事件**：驗收 = 給 N 個人玩、發一篇 devlog、投一次活動 demo——外部可見性製造真實的截止感。
- **驗收找人陪跑**：找一位開發者朋友互相當對方的驗收官，只需一小時看 build + 對門檻打勾。
- **不過就是不過**：自己對自己最容易「有條件過」。把「連續兩次不過就轉向/停案」寫成事先承諾。

## 常見陷阱

- **驗收會變成展示會**：只展示做得好的部分，門檻表沒打開。逐條打勾是唯一格式。
- **門檻臨場放水**：「15 分鐘改 10 分鐘也算啦」——門檻修改只能發生在階段開始，不能發生在驗收當天。
- **不過但捨不得**：投入越多越捨不得砍（沉沒成本），所以砍/轉向的規則要在投入前寫好。
- **回顧會開成情緒會**：聚焦三個問題、產出一項改善，超過一小時就是失焦。
