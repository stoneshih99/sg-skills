# 跑一場玩測

觀察紀律決定資料品質。同一場測試，主持得好是實驗，主持得差是陪玩。

## 找人

- **人數**：一輪 3-5 人就能抓到 8 成的重大問題；同一批問題重複出現就停，改完再測下一輪。
- **輪廓貼假設**：測「新手學習」找沒玩過的人；測「深度」找該類型老手。排除團隊成員與已看過開發過程的人（他們的盲區跟你一樣）。
- **一次一人**：兩人一起玩會互相教學、互相壯膽，教學與挫折的資料全毀（除非你就是要測多人）。

## 開場（一分鐘內講完）

只說三件事：

1. 「我們在測**遊戲**，不是測你。你卡住代表遊戲有問題。」
2. 「請邊玩邊說出你在想什麼（think-aloud）。」
3. 「我不會回答玩法問題——因為遊戲上市後我不在玩家旁邊。」

不要介紹操作、不要講背景故事、不要說「這裡還沒做好」——上市時你也不能在每個玩家耳邊講這些。

## 主持紀律（最難也最重要）

- **不出聲**：玩家卡住時閉嘴。開發者的每一句提示都在污染資料。卡住本身就是資料——記下位置與時長。
- **不救援**：真的完全卡死（超過你預設的上限，例如 5 分鐘）才用**中性話術**推進：「你要不要試試別的地方」，並在紀錄標記「此後資料受污染」。
- **不辯護**：玩家罵設計時不解釋「其實這是因為……」。點頭，記下來。
- **回問代替回答**：玩家問「這要怎麼用？」→「你覺得呢？你會想怎麼試？」——他接下來的嘗試就是教學設計的診斷（見 `level-teaching-through-design.md` 的開發者盲區）。

## 記錄什麼

用範本的觀察表，聚焦在**行為與時間點**：

- 卡點：位置、時長、脫困方式（想通 / 亂試 / 放棄）。
- 機制首次使用：第幾分鐘、主動還是誤觸。
- 情緒外顯：笑、罵、前傾、癱回椅背、看手機——記時間點，訪談時帶他回去。
- 意外用法：玩家用你沒想到的方式玩——這可能是 bug，也可能是金礦。

**能錄影就錄影**（含手元 / 按鍵顯示更好）。記憶會騙人，尤其當結果不如預期時。

## 測後

趁熱訪談（問法見 `playtest-asking-questions.md`），當天整理筆記——隔天你會忘掉一半細節。多人測完後彙整：**出現兩次以上的問題**優先處理，單一玩家的獨特意見降權。

## 常見陷阱

- **開發者本人主持自己的功能**：忍不住提示、忍不住辯護。可以的話換人主持，不行就用寫死的主持腳本綁住自己。
- **把玩測當展示**：demo 給發行商 / 朋友看是展示，有主持紀律的才是玩測。兩者混在一起兩頭空。
- **救援太快**：玩家卡 30 秒就出手，你永遠不知道他 60 秒後會不會自己想通——而「自己想通」正是設計成功的證據。
- **只記意見不記行為**：筆記全是「他說 UI 不好看」，沒有一條「第 4 分鐘在商店界面停了 90 秒沒買任何東西」。
