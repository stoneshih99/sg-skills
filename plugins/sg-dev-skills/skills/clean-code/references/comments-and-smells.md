# 註解紀律與 code smell

註解與 code smell 是同一個主題的兩面：**大多數註解是在補救本該由程式碼自己說清楚的事**，而 code smell 是「這裡的設計在發臭」的訊號。這篇是「該不該寫這註解、這 smell 該不該現在重構」的決策。

## 註解：寫 why，不寫 what

程式碼說明**做什麼（what）與怎麼做（how）**，註解只補程式碼無法表達的**為什麼（why）**：

```
i += 2;  // 每次跳兩格          ← 壞：重複程式碼已說的 what
i += 2;  // 跳過已被上一 pass 處理的偶數格，避免重複計費  ← 好：why，程式碼看不出來
```

**好註解**（程式碼表達不了的）：
- **為什麼這樣做**：不明顯的商業規則、繞過某 bug 的理由、為什麼不用看起來更直覺的做法。
- **警告後果**：「這裡不能改順序，X 依賴 Y 先初始化」。
- **法律/來源**：授權標頭、演算法出處、規格連結。
- **TODO/FIXME**：帶脈絡的待辦（但別讓它爛在那）。

**壞註解**（該刪或該改程式碼）：
- **複述程式碼**：`// 把 i 加一` ——噪音。
- **補救壞名字**：`int d; // 天數`——改名字，刪註解（見 [naming-for-intent.md](naming-for-intent.md)）。
- **被註解掉的程式碼**：版控會記得，刪掉——留著只會讓人不敢動。
- **過時註解**：比沒有更糟，因為它主動騙人。註解會腐爛（程式碼改了註解沒改）——所以能用程式碼表達就別用註解。

**判準**：想寫註解時先問「能不能改名字/抽函式讓它不需要這註解」。不能，才寫，而且寫 why。

## Code smell 目錄 → 對應重構

Smell 不是 bug，是「設計在提示該重構」的味道。認得味道，就知道往哪個手法走：

| Smell | 味道 | 對應重構 |
|-------|------|---------|
| **重複程式碼**（Duplicated Code） | 同段邏輯出現多處 | 抽函式 / 抽共用類別——但先確認是**真重複**（見下方 DRY 陷阱） |
| **重複條件分支**（Repeated Switches） | 同一條決策軸的 if-else/switch 散在多處 | 換多型或 strategy——結構選型見 `../../design-patterns/references/pattern-selection.md` |
| **過長函式**（Long Function） | 一句話說不清它做什麼 | 抽函式、拆抽象層級（見 [function-design.md](function-design.md)） |
| **過大類別**（Large Class） | 一個類別扛太多職責 | 拆類別、依職責分組 |
| **長參數列**（Long Parameter List） | 4+ 參數 | 包成參數物件 |
| **發散式修改**（Divergent Change） | 改一個需求要動同一類別很多地方 | 一個類別一個變更理由（SRP），拆開 |
| **散彈式修改**（Shotgun Surgery） | 改一個需求要動很多類別 | 相反問題：把該聚的邏輯聚回一處 |
| **依戀情結**（Feature Envy） | 方法一直在動別的類別的資料 | 把方法搬到資料所在的類別 |
| **基本型別偏執**（Primitive Obsession） | 用 string/int 表達本該有型別的概念（錢、電話、座標） | 引入值物件（Value Object） |
| **資料泥團**（Data Clumps） | 同一組欄位老是一起出現 | 包成物件 |
| **可有可無的註解** | 靠註解解釋爛程式碼 | 改名/抽函式讓註解變多餘 |

## DRY 的陷阱：假重複比重複更貴

DRY（Don't Repeat Yourself）被過度套用時反而製造耦合。**兩段程式碼長得一樣 ≠ 該合併**：

- **真重複**：同一個知識/規則出現多處，改需求時**必須同時改**——該抽。
- **假重複（巧合相同）**：現在剛好長一樣，但代表**不同的商業概念**、未來會各自演化——抽了之後，一邊的需求變了就得加參數/分支污染共用函式，比重複更痛。

**判準**：問「這兩處未來會**因為同一個理由**一起改嗎」。會→抽（DRY 針對的是知識重複）；只是恰好相同→先讓它重複，等第三次出現、模式清楚了再抽（Rule of Three）。

## 何時重構、何時放著

Smell 不是「立刻全修」的命令。重構要挑時機：

- **在你正要改的程式碼上重構**（童子軍原則：離開時比來時乾淨一點）——不為重構而重構、不順手大改無關區域。
- **重構前先有測試**（或先補），否則你是在沒有安全網下改行為。
- **會痛才修**：一個 smell 若在一段從不改動、也沒 bug 的角落，放著的成本可能低於動它的風險。乾淨是為了「好改」，不是潔癖。
- **別和硬規則混淆**：命名風格、排版是團隊/語言硬規則（CLAUDE.md/linter/formatter 管），不是這裡的重構判斷——那些交給工具自動化，別手動爭。

## 常見坑

- **註解複述程式碼**：`// i 加一`——噪音，刪。
- **靠註解補救壞名字/爛結構**：改名/抽函式，讓註解變多餘。
- **註解腐爛**：程式碼改了註解沒改，主動騙人——能用程式碼表達就別靠註解。
- **留被註解掉的程式碼**：版控記得，刪掉。
- **DRY 過度套用**：合併假重複，之後用參數/分支污染共用函式——問「會不會因同一理由一起改」，否則等 Rule of Three。
- **為重構而重構**：無關區域大改、沒測試就動——童子軍原則 + 先有測試 + 會痛才修。
- **把風格當 smell**：排版/大小寫交給 formatter/linter，別當手動重構目標。
