# 命名：表達意圖

名字是最便宜的文件，也是最常被浪費的。好名字讓程式碼不需要註解；壞名字讓讀的人每次都要回去查定義。這篇是命名的決策，不是命名慣例（大小寫風格留 CLAUDE.md）。

## 核心判準：名字要能回答問題

一個好名字回答三件事：**這是什麼、為什麼存在、怎麼用**。若名字需要旁邊補一行註解才懂，就是名字沒取好——把註解的內容塞進名字。

```
d           # 錯：d 是什麼？
elapsedDays # 對：名字自帶單位與意義
// 經過的天數
int d;      # 錯：靠註解補救壞名字
```

## 揭露 why，不只 what

變數/函式名描述**用途或意圖**，不是實作或型別：

- `list1` / `theList` → `activeAccounts`（它裝什麼、為什麼是這群）
- `flag` → `isEligibleForRefund`（這個布林代表什麼決策）
- `getData()` → `fetchOverdueInvoices()`（拿什麼、隱含來源）

**魔術數字換成具名常數**——`if (age >= 18)` 的 `18` 換成 `LEGAL_ADULT_AGE`，名字就是那個 why。

## 該避免的

| 反模式 | 問題 | 改法 |
|--------|------|------|
| **誤導性名字** | `accountList` 其實不是 List 而是 Set | 名字別綁錯資料結構；不確定就用 `accounts` |
| **編碼/前綴** | 匈牙利命名 `strName`、`m_count` | 現代 IDE 有型別提示，編碼是噪音（`_` 私有前綴等團隊硬規則例外，那屬 CLAUDE.md） |
| **心智映射** | 迴圈用 `i/j/k` 巢狀後要記誰是誰 | 短作用域的 `i` 可接受；一旦要「記住 x 代表什麼」就換有意義的名 |
| **不可搜尋** | 單字母、`5` 散落各處 | 具名常數 / 有意義的名字，能 grep 得到 |
| **無意義區分** | `data` / `data2` / `dataInfo` | 講清楚差異：`rawData` / `parsedData` |

## 決策：名字長度 vs 作用域

**作用域越大、名字越該完整**；作用域越小越可短：

- 一行迴圈的索引 `i`、lambda 的 `x`：短的可以，讀者一眼看完整個作用域。
- 跨越整個類別/模組的欄位、公開 API：完整表意的名字，因為讀者不會同時看到定義與用途。
- **反過來錯**：全域用 `n`、三行迴圈用 `currentIterationIndex`——都是沒對齊作用域。

## 一致性：同一概念同一詞

整個 codebase 用**同一個動詞表同一個動作**——別 `fetch`/`get`/`retrieve`/`load` 混用指同一件事。讀者靠詞彙建立心智模型，混用就是製造假區分。挑一組動詞表（get vs fetch vs compute 各有固定語意）並貫徹。

## 常見坑

- **靠註解補救壞名字**：`int d; // 天數`——把意義放進名字，刪掉註解。
- **名字綁實作/型別**：`accountList` 之後型別改了名字就騙人——描述用途不描述容器。
- **魔術數字/字串散落**：不可搜尋、改一處漏一處——具名常數。
- **同概念多個詞**：`fetch`/`get`/`load` 混用同一動作——製造假區分，統一動詞。
- **過度縮寫**：`calcTermFreqNorm`——省幾個字元，換讀者每次解碼。
- **把風格慣例當 clean code**：大小寫、底線前綴是**團隊/語言硬規則**（CLAUDE.md），不是這裡的決策——別在這層爭。
