# 行為型選型（Behavioral）：Strategy / State（FSM）/ Observer / Command

行為型的共同主題是**把「會變的行為」從「不變的骨架」裡抽出來**。每個 pattern 的進場訊號不同——訊號沒出現就別上。

## Strategy：訊號是「同一條決策軸的 if-else 長在多處」

- **一處 switch 不是訊號**（switch 沒有罪）；**同一軸的分支蔓延到第二、三處**才是——把該軸抽成可替換的策略，分支收斂回一個選擇點。
- 實作光譜：**有一等函式的語言，strategy 常常就是傳函式/lambda**——別為一個方法開介面加三個類。行為需要自帶狀態或多個方法才升級成物件。
- **表驅動是 strategy 的資料版**：`型別 → 行為參數` 查表——行為差異能參數化就進表（資料驅動的核心，遊戲版見 **sg-game-dev-skills** 的 data-config-driven），參數化不了才用程式碼策略。
- **Template Method 是同題的繼承解**：骨架在基類、變化點是抽象方法——預設選 strategy（組合），template method 留給「骨架與變化點天然同族、且語言慣例如此」的場合。

## State / FSM：三種實作，按規模選

| 實作 | 適用 | 崩點 |
|------|------|------|
| **enum + switch** | 狀態 ≤5、行為差異小 | 每加狀態改所有 switch |
| **State 物件**（狀態=類，含 enter/exit） | 行為隨狀態大幅改變、狀態有進出邏輯 | 類數量與樣板碼 |
| **轉移表**（資料驅動：狀態×事件→新狀態） | 轉移規則密集、要可設定/可視化 | 行為還是要掛回程式碼 |

- **FSM 的崩潰訊號是狀態組合爆炸**（Jump、JumpWhileAttacking、JumpWhileAttackingStunned…）——該分層（HSM）或換架構；遊戲 AI 的 FSM vs Behavior Tree vs Utility 裁決在 **sg-game-dev-skills** 的 system-game-ai，本篇只管 pattern 實作選擇。
- enter/exit 是 state 物件的真價值——資源掛接/清理有明確的家（動畫狀態機的 OnEnter/OnExit 同構）。

## Observer / Event：解耦的紅利，生命週期的債

- **進場訊號**：A 變化、B C D 要反應，但 A 不該認識它們——反向依賴（UI 更新、成就系統、音效觸發都是訂閱方）。
- **兩筆必收的債**：
  1. **訂閱洩漏**——訂了不退，物件死了 handler 還活著（記憶體洩漏＋對死物件呼叫）。紀律：**訂閱綁 owner 生命週期**，成對出現。
  2. **派發時機**——即時派發會重入（事件處理中又發事件，呼叫鏈深不可測）；佇列派發延遲一幀但可控。**全系統選一種並寫死**。
- 事件通道的完整設計（時機、優先序、除錯）是基礎設施題——遊戲版深化見 **sg-game-dev-skills** 的 system-foundation。

## Command：訊號是「動作需要被存起來」

- 動作要 **undo/redo、回放、巨集、排隊、網路轉送**其中之一——把「意圖」物件化（含執行所需的一切資料，最好可序列化）。**沒有這些需求，函式呼叫就是函式呼叫**，別包。
- undo 的實作岔路：command 記「反向操作」vs 記「執行前快照」——操作可逆用前者（省記憶體），不可逆或難算逆操作用後者。
- 遊戲的 input buffer、回放系統、網路輸入同步全是 command 的化身（輸入序列化——**sg-game-dev-skills** net 家族的輸入同步同源）。

## 常見坑

- **strategy 只有一個實作**：介面＋工廠＋一個策略類=三層儀式包一個函式——等第二個實作出現再抽。
- **observer 鏈式雪崩**：事件處理發事件再觸發事件——重入保護或佇列派發，並給事件鏈上除錯日誌。
- **FSM 硬撐組合爆炸**：狀態名出現「While」就是分層訊號。
- **command 沒帶 undo 資料**：要做 redo 才發現 command 只記了「做什麼」沒記「怎麼還原」——設計期定 undo 策略。
- **每個方法呼叫都事件化**：間接性有成本——單一接收者、同步、必然存在的依賴，直接呼叫就好。
