# 場景管理（Scene Management）

場景是**世界內容的載入單位與生命週期容器**。這篇管三件事：切換怎麼流、多場景怎麼組合、大世界怎麼串流。畫面層的流程（選單導航）是另一回事——那是 `system-ui.md` 的畫面堆疊；場景流與畫面流的關係在 `../../game-diagrams/references/game-flow-diagram.md` 一張圖看清。

## 切換流程：一個管理器，一條固定管線

**問題**：load 呼叫散落各處（門觸發器一個、選單按鈕一個、死亡重生一個），各自的清理與載入順序不一致——切場景的 bug 永遠修不完。

**解法**：場景切換只有一個入口，走固定管線：

```
scene_manager.transition(target, params):
1. 凍結輸入、fade out
2. 廣播 will_unload（各系統收尾：存檔快照、斷開場景參照）
3. unload 舊內容場景（驗證：事件訂閱歸零、場景域資源釋放——見 system-foundation）
4. async load 目標場景（進度餵 loading 畫面）
5. 初始化順序執行（場景系統 init → 內容 spawn → 玩家放置）
6. 廣播 scene_ready、fade in、解凍輸入
```

- **載入畫面是真實節點**（game-flow 的原則）：純黑閃切還是可互動 loading（跑酷小遊戲/提示輪播）是設計決策，但管線位置一樣。
- **params 帶入場資訊**：從哪個門進來、重生點 id——目標場景讀 params 決定玩家位置，**不要**用「上個場景直接改下個場景的物件」這種穿越操作。
- `will_unload`/`scene_ready` 走 foundation 的事件通道——系統對場景切換的反應收在各自系統裡，切換管理器不用認識任何人。

## Additive 組合：場景是積木

單一巨場景（一關一個檔）之外的正解是**組合**：

```
常駐場景（bootstrap）  systems、玩家、主相機、HUD——遊戲全程不卸載
  + 內容場景           地形、關卡邏輯、敵人佈置——按需載卸
  + 子場景（可選）      光照/美術與邏輯分檔——多人協作不打架（見 build-version-control 的場景衝突對策）
```

- **常駐場景解決「跨場景物件」的歸屬**：玩家、相機、音訊監聽器住在常駐場景——「換場景要不要搬玩家」這個問題直接消失。
- **多場景共存的全域查詢陷阱**：「找主相機」「找玩家」這類全域查詢（by tag/type/name）在多場景下會撿到**殘留的同類物件**——舊場景還沒卸完、或誰忘了刪測試用相機，查詢就撿錯，症狀是座標轉換全部飄掉這種難追的錯。**解法**：跨場景關鍵物件走服務註冊（`system-foundation.md` 的 registry），註冊/註銷綁生命週期，全域查詢只留給除錯工具。
- **場景間永不直接互抓物件**：跨場景溝通走 id + 事件 + 服務三件套（UI 的 id 原則、foundation 的事件——同一套紀律的場景版）。直接參照 = 卸載順序決定誰先懸空。

## 串流（大世界才需要）

固定關卡制用上面兩節就夠；開放世界加這層：

```
世界切成 chunk 網格（尺寸 = 視距與記憶體的折衷）
玩家位置 → 三環判定：
    load ring（預載半徑）＞ active ring（模擬半徑）＞ unload ring（卸載半徑）
```

- **load 與 unload 半徑必須不同**（遲滯）：同一半徑會讓玩家在邊界來回走時瘋狂載卸——unload ring 比 load ring 大 1-2 個 chunk。
- **載入非同步、實例化分幀**：I/O 非同步之外，大量物件的實例化本身會卡主執行緒——分幀鋪設（`../../game-tooling/references/perf-optimization-playbook.md` 的 time-slicing），優先鋪玩家前進方向。
- **AI 與模擬的降級跟著環走**：active ring 外的實體休眠或降頻（`system-game-ai.md` 的距離分級）——串流環就是模擬 LOD 的分界線。
- **浮點原點偏移**：離原點數公里後浮點精度開始抖（動畫、物理、渲染全遭殃）——大世界要做 origin shift（世界座標周期性平移回原點附近），且第一天決定，因為它污染所有「存世界座標」的系統（存檔、網路同步的座標都要跟著設計）。
- 串流世界的網路同步：AOI 與 chunk 天然對齊（`net-server-architecture.md` 的 interest management）。

## Spawn 管理

- **spawn point 資料化**：位置、類型、條件（首次/重生/波次）是場景資料，不是場景裡藏一堆手擺的 spawner 腳本各自為政（config-driven 的場景版）。
- **順序紀律**：`scene_ready` 之後才 spawn——場景還在載就生怪，落地在未載入的地形下面。多人下這條升級成雙端就緒握手（`net-server-architecture.md` 的房間生命週期）。
- 生成走物件池（perf 的池化），池的預熱掛在載入管線的第 5 步——載入期付成本，遊玩期零配置。

## 常見陷阱

- **load 呼叫散落**：本篇第一節。切換管理器是唯一入口，code review 盯這條。
- **卸載不乾淨**：舊場景的事件訂閱、計時器、全域註冊殘留——「上一關的 boss 血條出現在下一關」。foundation 的訂閱綁 owner + 卸載時驗證歸零（除錯：卸載後 dump 殘留訂閱，見 `../../game-tooling/references/debug-logging.md`）。
- **全域查詢撿錯物件**：多場景下 by tag/name 查詢的殘留陷阱（上面 Additive 節）——服務註冊取代全域查詢。
- **同步載入「小東西」**：一扇門後的房間「很小所以同步載」——累積起來就是每扇門卡一下（perf 的載入 spike）。管線只有非同步一條路。
- **串流無遲滯**：邊界抖動載卸，I/O 與 GC 雙殺。
- **大世界後期才發現浮點抖**：origin shift 的補救成本隨系統數量成長——大世界專案第一週就決定。
