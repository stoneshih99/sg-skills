# 網路同步與純資料

資料與行為分離的另一大紅利：當遊戲狀態是**純資料**時，序列化、存檔、網路複製都變簡單——要傳 / 要存的就是那些資料本身，行為不需要跟著走。

## 為什麼純資料好同步

- **可序列化**：純資料（欄位 + id 參照）能直接轉成 bytes；含方法 / 指標 / 隱藏狀態的物件不行。
- **狀態即真相**：世界狀態完整由資料描述，複製資料就複製了狀態。
- **易 diff**：兩份資料快照可比對出差異，只傳變動部分。

## 序列化基礎

- **用 id / 索引參照，不用指標**：跨機器指標無意義；實體互參一律存 id，接收端再重組。
- **明確 schema 與版本**：欄位順序 / 型別固定，並帶版本號以支援向後相容。
- **緊湊格式**：頻繁傳輸用二進位（固定欄位或 varint），不要傳冗長文字格式。

```
function serialize_entity(e):
    write_u32(e.id)
    write_fixed(e.position.x); write_fixed(e.position.y)
    write_u16(e.hp)
    # 只寫純資料欄位，不寫行為
```

## 快照（Snapshot）與 Delta

- **快照**：某一時刻整個（或相關）世界狀態的資料拷貝。
- **Delta（差異）壓縮**：只傳「這幀相對上一個已確認快照改了什麼」，大幅省頻寬。
- **狀態複製**：伺服器定期送快照 / delta，客戶端套用到本地資料。

```
function make_delta(prev, curr):
    changes = []
    for id in curr.entities:
        if id not in prev or curr[id] != prev[id]:
            changes.append((id, curr[id]))
    for id in prev.entities:
        if id not in curr: changes.append((id, REMOVED))
    return changes
```

## 決定論（Determinism）

若相同輸入必然產生相同結果，就能只同步**輸入**而非整個狀態（lockstep）：每台機器各自用同一份純資料 + 同一套系統跑出同樣世界。

- **好處**：頻寬極省（只傳玩家指令），常見於 RTS。
- **前提**：純資料 + 無隱藏狀態的系統、固定時間步、避免非決定來源（浮點差異、亂序遍歷、未定種子的亂數）。
- **對照**：狀態複製（傳快照 / delta）容忍不決定性，但頻寬較高。兩者依遊戲類型取捨。

## 客戶端預測與校正

即時遊戲為了手感，客戶端會先本地預測（立刻套用自己的輸入），再用伺服器權威狀態校正：

- 本地先跑，收到權威快照後比對，若偏差就回滾到權威狀態並重放這之後的本地輸入（reconciliation）。
- 純資料讓「保存過去幾幀狀態以便回滾重放」變得可行——狀態就是可拷貝的資料。

## 遊戲情境

- RTS：決定論 lockstep，只傳指令。
- FPS / 動作：狀態複製 + 客戶端預測 + 回滾校正。
- 存檔 / 回放：同一套序列化，回放 = 重新套用記錄下來的快照或輸入序列。

## 陷阱

- **序列化含行為 / 指標**：物件帶方法或指向別處的參照就無法乾淨序列化；保持資料純粹、用 id 參照。
- **忽略版本相容**：格式一改，舊存檔 / 舊客戶端就爆；一開始就帶版本號與遷移策略。
- **決定論的浮點陷阱**：不同平台 / 編譯浮點結果可能不同，決定論模擬對此極敏感，必要時用定點數。
- **無防作弊思維**：客戶端資料不可信，權威狀態應在伺服器；預測只影響表現，不決定結果。
- **全量傳輸**：每幀送整個世界狀態會塞爆頻寬；用快照 + delta，並依重要性 / 距離調同步頻率。
