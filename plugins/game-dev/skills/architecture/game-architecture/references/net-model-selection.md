# 同步模型選型（Net Model Selection）

多人架構的第一個決策，也是最難回頭的決策：**權威放哪、同步什麼**。選錯的重構成本是「整個 gameplay 層重寫」等級——所以這篇放在 net 家族第一篇。序列化與快照的基礎見 `data-network-sync.md`（入門篇），本篇是裁決層。

## 兩軸定位：權威 × 同步物

**軸一：權威在哪**

| 模式 | 信任結構 | 適合 | 代價 |
|------|---------|------|------|
| **專用伺服器** | 伺服器全權威，客戶端只是視圖 | 競技、有經濟的遊戲——一切防作弊的前提 | 伺服器成本、你要寫兩端 |
| **Listen server（玩家當主機）** | 主機權威 | 好友合作、小規模 | 主機優勢（零延遲）、主機跑路 = 全場斷線 |
| **P2P + 決定論** | 沒有權威，人人模擬 | 格鬥（rollback）、RTS（lockstep） | 需要嚴格決定論；反作弊弱（看穿型作弊防不了） |

**軸二：同步什麼**

| 模型 | 傳什麼 | 頻寬 | 前提 |
|------|--------|------|------|
| **鎖步（lockstep）** | 只傳輸入 | 極省 | **嚴格決定論**（見 data-network-sync 的浮點陷阱）；延遲 = 等最慢玩家 |
| **回滾（rollback）** | 輸入 + 本地先行模擬，晚到的輸入回滾重放 | 極省 | 決定論 + 狀態快照廉價 + 重模擬快（一幀內重放數幀） |
| **權威狀態同步** | 伺服器算，下發狀態（快照/delta），客戶端預測補體感 | 較高 | 不需決定論；體感靠預測層（見 `net-prediction-and-latency.md`） |

## 按類型的建議起點

| 遊戲類型 | 建議 | 為什麼 |
|----------|------|--------|
| 格鬥 / 1v1 動作 | P2P 或中繼 + **rollback** | 幀精度要求極高、實體少（快照小、重模擬快） |
| FPS / 多人動作 | **專用伺服器 + 狀態同步 + 預測 + 延遲補償** | 防作弊剛需、實體中量、決定論難以維持 |
| RTS / 大量單位 | **lockstep** | 千單位的狀態同步頻寬不可行，輸入同步是唯一解 |
| 合作 PvE（2-4 人） | Listen server + 狀態同步，驗證從寬 | 成本低；作弊只傷朋友，不值得專服 |
| 回合制 / 非同步 | 伺服器權威 + 指令驗證 | 沒有即時性問題，重點在校驗與斷線續行 |

**動作遊戲的預設解**：專用伺服器 + 狀態同步 + 客戶端預測——除非你在做格鬥遊戲（那就去啃 rollback），否則從這裡開始。

## Rollback 的入場費（想選它先看這段）

Rollback 體感最好（本地零延遲），但門檻具體且不可繞過：

1. **嚴格決定論**：同輸入必同結果——固定步長、定點數或嚴控浮點、有序遍歷、可重現亂數（種子管理見 `../../../tools/game-tooling/references/debug-logging.md` 的 seed 記錄）。
2. **狀態快照要廉價**：每幀可存/可還原全 gameplay 狀態——純資料結構是前提（`data-separation.md` 的紅利在這裡兌現）；帶指標與行為的物件圖做不到。
3. **重模擬要快**：回滾 7 幀 = 一幀內重算 7 幀 gameplay——模擬層必須與渲染層完全分離（見 `system-3c.md` 的邏輯/渲染分離）。
4. 表現層要能「吞」回滾：音效不重播、特效不閃爍——表現事件去重。

四條有一條做不到，退回狀態同步。**這些前提都是第一天的架構決策**，做完遊戲再加 rollback 是重寫。

## 混合是常態

單一模型純用很少見，常見的混法：

- **房間內狀態同步 + 房間外 Req/Resp**：戰鬥即時同步，背包/商店/配對走一般請求（協定分層見 `net-protocol-and-connection.md`）。
- **關鍵資產雙重驗證**：即使 lockstep/P2P，經濟結算仍過中央伺服器校驗（誰贏了、掉了什麼）。
- **權威分割**：位置伺服器權威、表情動作客戶端權威——**不影響勝負的東西可以下放**，這是頻寬與體感的免費午餐。

## 常見陷阱

- **「先做單機之後加連線」**：同步模型影響 gameplay 層的每一行（狀態怎麼存、邏輯怎麼 tick）——多人是架構屬性不是功能。至少在 foundation 期決定「要不要、哪種」（見 `system-foundation.md` 的地基原則）。
- **選了 lockstep 才發現決定論守不住**：跨平台浮點、物理引擎、第三方庫都是決定論殺手——選前先做決定論 spike（風險驗證，見 `../../../planning/game-design/references/gdd-risk-assessment.md` 的技術風險）。
- **P2P 做競技**：看穿型作弊（讀記憶體開全圖）在 P2P 無解——有排名就要權威伺服器。
- **過早煩惱萬人同服**：房間制（見 `net-server-architecture.md`）能撐住絕大多數遊戲——大世界分片是另一個量級的工程，需求出現前別碰。
