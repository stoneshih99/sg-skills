# 階段定義

每階段一個問題、一個門檻。最常見的專案病是「階段錯位」——在 prototype 打磨美術、到 beta 還在改核心玩法。這篇是對照表，用來診斷「我現在到底該做什麼」。

## Prototype（原型）

**問題：核心循環好玩嗎？**

- **做**：核心循環的最小可玩版本；灰盒美術、佔位音效、鍵盤人偶。快、醜、可玩。
- **不做**：任何打磨（美術、音效、UI 動效）、任何周邊系統（存檔、設定、成就）、超過一種的內容變化。
- **門檻範例**：外部測試者（非團隊）3/5 人主動玩超過 15 分鐘、能說出想再玩的理由（驗法見 `../../../planning/game-design/references/playtest-hypothesis-and-metrics.md`）。
- **時長感**：數天到數週。超過一個月的 prototype 通常是在偷做正式版。
- **殘酷規則**：不好玩就砍掉重來或轉向——prototype 的產出是**答案**，不是程式碼。程式碼全扔也算成功。

## Vertical Slice（垂直切片）

**問題：完整品質的體驗成立嗎？**

- **做**：一小段（一關/十分鐘）**發售品質**的完整體驗：美術、音效、手感（見 `../../../planning/game-design/`）全到位；建立品質標竿與製作管線。
- **不做**：量產內容、全部系統——切片外的東西維持灰盒或不存在。
- **門檻範例**：外測者無提示通關該段落、體驗評價正向；團隊確認「照這個品質做 N 關，單位成本是 X」（這個數字餵給範圍決策，見 `../../../planning/game-design/references/gdd-scope-cutting.md`）。
- **附帶產出**：單位內容的實測成本——這是 alpha/beta 排程的唯一可信依據。

## Alpha（系統完備）

**問題：系統齊了嗎？（Feature Complete）**

- **做**：所有系統與機制進入可玩狀態；全流程能從頭走到尾（內容可以是佔位）；除錯工具齊備（見 `../../../tools/game-tooling/`）。
- **不做**：加新系統（**封機制**，feature freeze 從此開始）、精修平衡（系統沒齊之前的平衡都是白調）。
- **門檻範例**：主流程 100% 可通（允許醜與 bug）、每個系統至少一個實例可玩、無「還沒做」的系統性缺口。
- **常見病**：「還想加一個系統」——加進來的每個新系統都讓 beta 的穩定期重算。想加的記到續作/更新清單。

## Beta（內容完備）

**問題：內容齊了嗎？穩定嗎？（Content Complete）**

- **做**：全部內容進版；平衡輪調（先粗後細）；bug 修復優先於一切；效能達標；本地化與平台合規。
- **不做**：加新內容、改核心系統——此時改核心等於把前面的驗證全部作廢。
- **門檻範例**：內容 100% 進版、崩潰率低於目標、主流程無 blocker bug、外測（較大樣本）的平衡回饋收斂。
- **心理準備**：beta 是最漫長無聊的階段，進度感最低。這是正常的，不是專案出問題。

## Gold / 上線

**問題：能交到玩家手上嗎？**

- **做**：發佈候選版（RC）、平台審核、商店頁素材、Day-1 patch 清單、上線監控與回報通道。
- **不做**：任何「順手改一下」——RC 之後每個改動都要重跑驗證，改一行也一樣。
- **門檻範例**：RC 通過全回歸清單、平台審核通過、回報通道就緒。

## 階段錯位自我診斷

- 在 prototype 調粒子特效 → 提前打磨，回去驗核心。
- 在 vertical slice 做第 8 關 → 提前量產，先把一關做到位。
- 在 alpha 還在猶豫要不要加系統 → 封機制的紀律問題。
- 在 beta 改操作手感 → 高危：手感牽動全部平衡與教學，除非玩測證據壓倒性。
- 任何階段說「先做了之後再驗」→ 順序反了，門檻先行。
