# 量測方法論

優化的第一步永遠不是改碼，是回答三個問題：**多慢？慢在哪？跟誰比？**

## 幀預算（Frame Budget）

把目標寫成毫秒，不是 fps——fps 是非線性的，毫秒才能做算術：

| 目標 | 幀預算 |
|------|--------|
| 60 fps | 16.6 ms |
| 30 fps | 33.3 ms |
| 90 fps（VR） | 11.1 ms |

- **在最弱目標裝置上分配預算**：開發機跑 200fps 毫無意義。預算表範例（60fps）：邏輯 4ms、物理 3ms、渲染 6ms、其他 2ms、**保留 1.6ms 餘裕**。
- **餘裕不是浪費**：吃滿預算的遊戲，一個粒子高峰就掉幀。常態負載目標訂在預算的 80%。
- 幀率之外的預算軸：**記憶體**（目標裝置上限）、**載入時間**（可接受秒數）、**電量/發熱**（行動裝置）。

## Spike vs 均值：兩種不同的病

- **均值高**（持續 20ms/幀）：整體太重——找最大占比的系統砍。
- **spike**（平常 10ms，偶爾 80ms）：突發卡頓——找「偶爾發生的事」：GC、載入、生成大量物件、第一次使用的編譯/快取。**spike 在均值圖上會被平均掉**，要看逐幀圖與最差幀（1% low）。
- 玩家對 spike 遠比對均值敏感：穩定 30fps 的體感好過平均 50 但常跳 spike。

## Profiler 使用紀律

- **先看全景再鑽細節**：先分 CPU vs GPU（誰先吃滿預算），再分系統，最後才到函式。順序反了會在 0.1ms 的函式上浪費一天。
  - CPU bound：降解析度幀率不變。GPU bound：降解析度就變快。
- **量測本身有成本**：深度 instrumentation 會扭曲時間分佈；先用低開銷的取樣模式找方向，再對嫌疑區精確計時。
- **固定測試場景**：選 2-3 個代表性重負載場景（最多敵人、最多特效），每次量測同場景同路線——不可比的數字沒有意義。做成一鍵指令（見 `debug-console-and-cheats.md` 的情境書籤）。
- **在目標裝置量**：不同硬體瓶頸完全不同（桌機 GPU 強、手機頻寬窄）。開發機的 profile 只能參考結構，不能當結論。
- **記錄基準**：每次優化前存一份數字（場景、裝置、各系統毫秒）。沒有 before，就沒有「變快了」的證據。

## 內建計時面板

Profiler 之外，遊戲內常駐一個輕量計時層（配 `debug-draw.md` 的 watch 面板）：

```
scoped_timer("AI"):        # 進出自動計時
    update_ai(dt)
# 面板顯示：AI 2.1ms | Physics 3.0ms | Render 5.8ms | Total 12.4ms
```

- 隨時可見，效能退化當天就會被發現，而不是三週後。
- 單幀超預算自動 log 摘要（見 `debug-logging.md` 的效能異常埋點）。

## 常見陷阱

- **憑感覺鎖定嫌疑犯**：「一定是尋路太慢」——量下去是每幀字串拼接。感覺只能決定先量哪裡，不能決定改哪裡。
- **在 debug build 量測**：沒開優化的組建，時間分佈與 release 完全不同。量測一律用接近出貨設定的 build。
- **改了不回測**：優化後只看「感覺有沒有變順」。同場景數字對比，沒變快就還原。
- **只量一次**：熱機、快取、背景程序都會讓單次量測波動；取多次的中位數。
