# 衝突解決

合併衝突不是錯誤，是 git 說「這兩邊改了同一處，我不敢替你決定」。這篇是讀懂衝突、有紀律地解、和讓 git 記住你的解法。

## 讀懂衝突標記

衝突的檔案會出現三段標記：

```
<<<<<<< HEAD
你這邊（當前分支）的版本
=======
對方（要合入的分支）的版本
>>>>>>> feature-branch
```

- `<<<<<<< HEAD` 到 `=======`：**你當前分支**的內容。
- `=======` 到 `>>>>>>>`：**要合入的那邊**的內容。
- **解法 = 編輯成最終想要的樣子**（可能保留一邊、或兩邊融合、或都重寫），**刪掉三個標記行**，然後 `git add` 標記為已解決。

**rebase 時方向會反直覺**：rebase 是「把你的 commit 重放到對方頂端」，所以 `HEAD` 是**對方（目標分支）**、`>>>>>>>` 是**你正在重放的 commit**——跟 merge 相反。看標記後面的分支名確認，別憑直覺。

## 解衝突流程

```bash
# merge/rebase 遇衝突後
git status                      # 看哪些檔案衝突（Unmerged paths）
# 逐個編輯解決，刪掉標記
git add <解好的檔案>
# merge： git commit（完成 merge）
# rebase： git rebase --continue（繼續下一個 commit）

# 不想解了、回到起點：
git merge --abort   /   git rebase --abort
```

## 紀律

- **理解再解，別亂選一邊**：`git checkout --ours` / `--theirs` 整檔選一邊很快，但常常兩邊都有需要的東西——看懂衝突內容再決定。
- **衝突大 = 分支太久沒同步**：巨大衝突的根因通常是 feature 分支活太久（見 `branch-strategy.md` 分支短命）——頻繁 rebase/merge main 進來，把大衝突拆成小衝突。
- **解完要驗證**：解衝突是「手動編輯」，很容易解出**能編譯但邏輯錯**的結果——解完跑測試/建置，別只看沒標記了就 commit。
- **用工具看三方**：`git mergetool` 或 IDE 的三方合併視圖（顯示共同祖先 + 兩邊）比讀標記清楚，複雜衝突值得開。
- **`git checkout --conflict=diff3`**：讓標記多顯示**共同祖先**，看得出「兩邊各從什麼改過來」，判斷更準。

## rerere：讓 git 記住你的解法

長命分支反覆 rebase，同樣的衝突要解很多次——`rerere`（reuse recorded resolution）記住你解過的，下次自動套：

```bash
git config --global rerere.enabled true
# 之後解過一次的衝突，再遇到同樣的 git 自動重用你的解法
```

適合：長期維護的分支、反覆 rebase 的情境——解一次，之後同衝突免解。

## 常見坑

- **rebase 的衝突方向搞反**：以為 HEAD 是自己，其實 rebase 時 HEAD 是目標分支——看分支名不看位置。
- **無腦 `--ours`/`--theirs`**：整檔選一邊丟掉另一邊的必要改動——理解內容再選。
- **解完沒驗證**：解出能編譯但行為錯的合併——解完必跑測試。
- **忘了刪標記**：`<<<<<<<` 留在檔案裡進了 commit——`git add` 前檢查，或用工具。
- **大衝突硬解**：分支太久的巨型衝突——根治是分支短命 + 頻繁同步，不是更會解衝突。
