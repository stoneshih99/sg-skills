# UI 互動手感

UI 也有手感：按下去有沒有回饋、轉場快不快、焦點聽不聽話。原則與遊戲手感同源（見 `../../../planning/game-design/`），只是量級更收斂——UI 要俐落，不要炫。

## 回饋

每次互動三層回饋，全部在 100ms 內（同 input-responsiveness 的反應預算）：

- **視覺**：按下的瞬間有狀態變化（四態資產的 pressed 態，見 `art-asset-types.md`）+ 微縮放/亮度變化。
- **聽覺**：hover 與 click 分開的 UI 音（輕、短、同族，見 `audio-sfx-design.md` 的 UI 音層數）。
- **結果**：操作生效的證據——買了東西，金幣數字要動、物品要飛進背包。**操作與結果之間不能是靜默**。
- 失敗也要回饋：按了不能按的東西，給短促的「否定」訊號（抖動 + 低音效）——沉默會讓玩家連按三次。

## 轉場時長

- **UI 動畫預算：100-250ms**。低於 100ms 看不見（那就乾脆瞬切），超過 300ms 玩家開始等你——每天開幾十次的選單，0.5 秒的華麗轉場第三天就是折磨。
- **可跳過**：任何 UI 動畫在玩家再次輸入時立即完成——動畫服務理解（東西從哪來到哪去），不服務儀式感。
- **頻率反比原則**：越常見的操作動畫越短（切分頁 ~100ms），越罕見的可以越長（開寶箱結算可以演）。
- 緩動用 ease-out（快進慢停）——UI 要的是「響應快、落點穩」。

## 焦點導航（手把 / 鍵盤）

- **焦點永遠可見且唯一**：當前焦點的高亮要夠明顯（不只變色，加框/放大）——「我現在選到哪」一眼要知道。
- **方向對應空間**：按右就到視覺上右邊的元件——網格佈局天然合理，異形佈局要手動指定焦點鏈，別讓引擎猜。
- **邊界行為定義**：最右再按右——停住？繞回最左？跳下一組？全遊戲一致。
- **預設焦點 = 最可能的操作**：進對話框焦點在「確認」（危險操作除外：刪除類預設焦點在「取消」）。
- **記憶焦點**：返回上一頁時焦點回到來時的項目（同 hud-and-menus 的狀態保留）。

## 輸入方式適配

| | 滑鼠 | 手把 | 觸控 |
|--|------|------|------|
| 命中區 | 小可接受 | 焦點制（無命中區問題） | ≥ 44pt 實體尺寸 |
| hover | 有（提示浮窗可用） | 焦點即 hover | **沒有**——資訊不能只藏在 hover |
| 慣用操作 | 點擊、拖放 | 方向 + 確認/取消、肩鍵切頁 | 點擊、滑動、長按 |

- **同時支援多輸入時以最受限的設計**：手把逛得順的選單，滑鼠一定順；反之不成立。
- **輸入切換即時生效**：玩家摸了手把，提示圖示立刻換成手把鍵位——混顯 keyboard 提示給手把玩家是廉價感來源。
- **觸控的拇指熱區**：常用鍵放螢幕下半左右側（拇指自然範圍），危險鍵遠離熱區防誤觸。

## 常見陷阱

- **hover 藏關鍵資訊**：道具屬性只在滑鼠懸停顯示，手把與觸控玩家看不到——資訊要有無 hover 的替代路徑（焦點即顯示）。
- **轉場疊加**：連按切頁時動畫排隊，畫面慢半拍追輸入——新輸入殺掉進行中的動畫。
- **焦點丟失**：清單項目被刪後焦點消失，手把玩家卡死——焦點轉移規則涵蓋元素消失的情境。
- **UI 回饋比遊戲華麗**：選單特效比戰鬥還多——注意力稅倒收。UI 的存在感永遠低於遊戲本體。
