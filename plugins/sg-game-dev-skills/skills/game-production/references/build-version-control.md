# 遊戲版控

遊戲版控與一般軟體的差別在**資產**：大量二進位大檔（貼圖、模型、音訊）與難以合併的結構化檔（場景、prefab）。這兩件事第一天就要處理，資產灌進倉庫後再改代價高昂。

## 大檔案與二進位資產

- **LFS（或等效方案）第一天就開**：貼圖、模型、音訊、影片進 LFS；.gitattributes 按副檔名宣告。倉庫塞進 2GB 二進位歷史之後再遷移，是整個團隊陪你重 clone。
- **判斷線**：會被合併工具處理的文字檔走一般版控；其餘（含引擎序列化的大型資產）走 LFS。
- **超大來源檔另置**：PSD 原檔、錄音工程檔這類「產出資產的來源」考慮放雲端硬碟/資產庫，倉庫只進導出品——倉庫是給「建置需要的東西」的。
- **忽略清單第一天就設**：引擎快取、建置輸出、使用者偏好（`Library/`、`Temp/`、`*.csproj` 類自動生成物）——這些進了倉庫就是永無止境的假衝突。用該引擎的社群標準 .gitignore 起手。

## 場景與 Prefab 的合併問題

引擎序列化檔（場景、prefab、材質）名義上是文字，實際上幾乎不可手動合併——兩人同時改同一場景，衝突解起來像拆炸彈。對策按優先序：

1. **切小，避免共編**：大場景拆成子場景/區塊（additive 載入），每人各自負責的區塊各自一檔；共用元素做成 prefab 引用。**用結構避免衝突，勝過用工具解決衝突。**
2. **鎖定約定**：改場景前在團隊頻道喊一聲（或用檔案鎖工具）——低科技但對小團隊夠用。
3. **引擎的專用合併工具**：真的撞上了才用（如 Unity 的 Smart Merge），把它設為這類檔案的 merge driver。
4. **場景裡少放邏輯**：資料與參數外化（見 `../../game-architecture/references/data-config-driven.md`），場景檔越「薄」，衝突面越小。

## 分支策略（小團隊版）

- **main 永遠可建置**：這是唯一鐵律。壞 main 的 commit 立即修或立即 revert。
- **短命功能分支**：一個功能一個分支，數天內合回——分支活越久，資產衝突機率指數上升（二進位資產無法合併，撞上就是二選一）。
- **發版切 release 分支**：RC 凍結後從 main 切出（見 `build-release-checklist.md`），hotfix 進 release 再回灌 main。
- 個人開發可以直接 main + tag 發版點，但「main 可建置」照守——你的未來自己就是那個被壞 build 坑的隊友。

## Commit 紀律

- **資產與程式碼盡量分 commit**：回退程式碼時不至於連資產一起退。
- **可運行粒度**：每個 commit 是一個可建置的狀態；「WIP 半成品先推上去」用分支，不進 main。
- **訊息寫「為什麼」**：資產 commit 尤其要——「調暗第三章整體亮度（玩測回饋看不清敵人）」勝過「更新貼圖 x12」。

## 常見陷阱

- **第一天不設 LFS / ignore**：最常見也最貴的錯。專案模板把 .gitattributes + .gitignore 做進去。
- **把版控當備份**：建置輸出、錄影、整包外部資產庫全塞進來——倉庫肥到沒人想 clone。備份走備份方案。
- **長期分支大合併**：兩週不合的美術分支，合併日就是災難日。小步快合。
- **場景衝突用「選我的」解決**：二進位式衝突隨手選一邊，另一邊的工作靜默蒸發，兩週後才發現。撞上衝突先問對方改了什麼。
