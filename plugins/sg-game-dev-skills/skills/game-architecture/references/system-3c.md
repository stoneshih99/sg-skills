# 3C 系統（Character / Controller / Camera）

3C 是動作遊戲手感的架構地基：**Controller**（輸入 → 意圖）、**Character**（意圖 → 移動與狀態）、**Camera**（呈現與方向基準）。手感參數怎麼調見 `../../game-design/`（Feel 域）；這篇講**架構**——層怎麼切、兩種移動驅動怎麼選、更新順序為什麼會抖。

## 分層：輸入 → 意圖 → 執行

```
裝置輸入 ──► InputMap（動作映射）──► Intent（意圖，純資料）──► Character（執行）
             「跳躍鍵=Space/A」        { move: (0.7, 0.2),          讀 intent，
             可重綁的唯一地方           jump: pressed,               過能力鎖，
                                       attack: buffered }           驅動狀態機
```

- **InputMap 是唯一碰裝置的層**：遊戲邏輯只認「動作」（jump/attack），不認按鍵——重綁鍵、多裝置、錄製回放都在這層解決（重綁是無障礙基本盤，見 `../../game-production/references/ui-accessibility.md`）。
- **Intent 是純資料**：每幀一份「玩家想做什麼」的快照。好處三個：AI 與玩家共用 Character（AI 也產 intent，角色程式完全不知道驅動者是誰）、回放 = 錄 intent 序列、網路同步 = 傳 intent（決定論見 `data-network-sync.md`）。
- **input buffer 放在 intent 層**：緩衝的是「意圖」不是按鍵（見 `../../game-design/references/feel-input-responsiveness.md`）；Character 在可行動幀查詢 buffer。

**方向解算在 intent 層做**：搖桿的「前」是**相機的前**——`world_dir = camera_yaw_rotation × stick_input`。這就是 Camera 進 3C 閉環的原因：相機轉，同一個搖桿方向的世界意義就變。注意鏡頭快速旋轉（過肩鏡頭切換、鎖定切換）瞬間，玩家還按著的方向會突變——常見解法：**方向意圖在輸入持續期間鎖定解算基準**，鬆桿再重解。

## Character：兩種移動驅動

**模式 A：運動學控制器（kinematic）**——自己算位移，碰撞用掃掠查詢解決，不受物理引擎的力學支配：

- 優點：完全可預測、手感參數直接生效（加速度曲線就是你寫的那條，見 feel-movement）、不會被物理彈飛。
- 缺點：所有互動自己寫（推箱子、站上移動平台、被爆炸擊飛都要手動處理）。
- 適合：**平台跳躍、動作、格鬥——手感優先的一切**。

**模式 B：物理驅動（rigidbody + 力）**——角色是物理體，施力移動：

- 優點：與物理世界互動免費（碰撞反應、堆疊、載具）。
- 缺點：手感隔著一層積分器（想要「立刻停下」得跟摩擦力搏鬥）、幀率與物理步長影響行為。
- 適合：載具、物理沙盒、對「操控精確度」要求低的模擬類。

**選擇**：動作類幾乎都選 A，需要物理互動的點（被擊飛、載具）**局部切換**——擊飛瞬間轉交物理體，落地恢復 kinematic。切換點的狀態交接（速度傳遞）要顯式處理，這是混合方案唯一的坑。

**Kinematic 的必做清單**（每項都是「沒做就會被玩家罵」的）：

- [ ] **接地檢查**：向下掃掠 + 容差；結果進入狀態機（見 coyote time 的來源）。
- [ ] **斜坡**：可行走角度上限、坡上移動投影到坡面（否則上坡變慢下坡彈跳）、超過角度滑落。
- [ ] **台階**：小於 step height 的障礙自動跨上——沒有它，一顆小石頭擋死玩家。
- [ ] **移動平台**：站在平台上要繼承平台位移（parent 或速度疊加，各有邊角案例，速度疊加對旋轉平台較穩）。
- [ ] **貼地投射**：下坡時把位移貼回地面，否則跑下坡變成小跳步。

**狀態機與能力**：Locomotion/Action 雙機拆分與引用計數能力鎖見 `system-action-combat.md`（同一套，不重複）；root motion vs 程式位移的抉擇見 `../../game-production/references/anim-game-principles.md`。

## Camera：解算管線 + 優先權混合

相機不是「一顆跟著角色的物件」，是一條**每幀解算管線**：

```
1. 目標解算    跟誰、看哪（角色位置 + look-ahead 偏移）
2. 約束        碰撞（spring arm 掃掠避免穿牆）、邊界（關卡範圍）、
               死區（小位移不動鏡頭）
3. 平滑        位置/旋轉各自的阻尼（分開調！位置要跟緊、旋轉要柔）
4. 效果疊加    shake、FOV kick、後座力——加在最終輸出上，不污染狀態
```

- **每層只做一件事且順序固定**：平滑放在碰撞之後會讓鏡頭穿牆半秒；效果疊加放在平滑之前會被阻尼吃掉。
- **多相機源用優先權系統**：探索相機、鎖定相機、過場相機、瞄準相機——各自是一組參數（資料），啟用時按優先權混合過渡（blend 時間也是資料）。**不要**用一顆相機物件上的一堆 if；「新增一種鏡頭」應該是加一份資料（config-driven，見 `data-config-driven.md`）。
- **碰撞的細節**：spring arm 用球形掃掠（單射線會在邊角抖）；被推近後**恢復要慢**（快速彈回比穿牆更暈）；貼牆極近時淡出角色而不是讓鏡頭進到模型裡。
- 死區、look-ahead、垂直跟隨保守等**參數層**設計見 feel-movement 的攝影機節——架構的責任是讓那些參數各自獨立可調。

## 更新順序：抖動的第一嫌疑人

畫面抖動、角色殘影、鏡頭滯後一幀——九成是更新順序問題：

```
正確的一幀：
1. 輸入採樣 → intent
2. Character 更新（移動、狀態機）     ← 邏輯步
3. 動畫更新（骨架就位）
4. Camera 解算                        ← 一定在角色最終位置確定之後
5. 渲染
```

- **Camera 必須晚於 Character**：反過來就是永遠看著上一幀的位置——高速移動時的「橡皮筋感」。
- **物理步長與渲染幀率不同步時**（固定步長物理 + 高刷新渲染）：角色若走物理更新，渲染位置要**插值**，且相機跟的是插值後的位置——跟到原始物理位置就是規律性微抖。
- 用 game-tooling 的逐幀步進（`../../game-tooling/references/debug-time-control.md`）驗證：單步推進看每個階段的位置快照，順序錯誤一步可見。

## 常見陷阱

- **輸入直接驅動位移**：跳過 intent 層，`if key_pressed: pos += ...`——AI 接不進來、回放做不了、buffer 沒地方放。第一天就分層。
- **手感參數藏在物理材質裡**：選了模式 B 之後用摩擦係數、阻尼調手感——參數間接又互相牽連。手感優先就回模式 A。
- **相機邏輯長在角色身上**：角色腳本裡一段 camera 偏移計算——鎖定、過場一來就打架。相機是獨立管線，角色只是它的目標之一。
- **每種鏡頭一個相機物件常駐**：切換靠 enable/disable，狀態殘留與過渡生硬——單一相機 + 參數組混合。
- **移動平台用 parent 硬掛**：縮放與旋轉繼承出鬼、下平台忘了解除——速度疊加方案邊角少。
