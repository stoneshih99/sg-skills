# 自動化建置

「只有那台機器出得了 build」是專案的單點故障。自動化的目標：**任何人、任何時候、一個指令、同樣的 build**。

## 一鍵建置（第一步，先於 CI）

把「出一個 build」寫成一個腳本，收進版控：

```
build.sh [platform] [config]
  1. 檢查/還原相依（套件、子模組、LFS 拉取）
  2. 注入版本資訊（版本號、commit hash、build 時間）
  3. 呼叫引擎的命令列建置（headless）
  4. 建置後處理（壓縮、簽章、產出物歸位到 builds/<version>/）
  5. 失敗即中止並回報非零結束碼
```

- **消滅「機器狀態」依賴**：build 需要的一切（SDK 版本、環境變數、金鑰位置）寫在腳本或文件裡；換一台乾淨機器照文件能出 build，才算合格。
- **開發/發佈設定分離**：dev build 帶除錯工具與日誌，release build 剝離（見 `../../game-tooling/` 的發佈版剝離原則）——用建置參數切換，不用手動改碼。

## Build 編號與可追溯

每個 build 必須能回答「你是誰、從哪來」：

- **版本三件套**：語意版本（0.9.2）+ 遞增 build 號（#347）+ commit hash——顯示在主選單角落與日誌開頭（見 `../../game-tooling/references/debug-logging.md` 的載入與版本埋點）。
- **資料表版本一起記**：程式版本 × 資料版本才唯一決定行為（config-driven 的必然結果）。
- **產出物歸檔**：builds 按版本留存（至少留最近 N 版 + 每個里程碑版），玩家回報「上一版還好好的」時你要能立刻裝回上一版。

## CI（一鍵之後的第二步）

- **觸發**：至少「每次合入 main」跑建置——**main 可建置**這條鐵律，靠 CI 而不是靠自覺（壞了立刻通知，修復優先於新工作）。
- **夜間完整版**：每晚出全平台 build + 跑完整測試，早上看結果。開發中的「每週可玩版」（見 `milestone-planning-and-estimation.md`）直接取夜間版。
- **快取要做**：遊戲建置動輒數十分鐘，引擎資產快取、套件快取沒設好，CI 慢到沒人理它。
- 個人開發的最小版：本機 cron / 手動每日跑一次 build 腳本，也遠勝於「要用才 build」。

## 多平台

- **平台矩陣寫進腳本**：`build.sh all` 依序出全平台；平台特定設定（圖示、簽章、SDK）全部參數化。
- **最弱平台優先建**：效能與相容問題在最弱目標平台最先炸（見 profiling 的目標裝置原則）；別到發版週才第一次在手機上跑。
- **平台差異集中管理**：條件編譯/平台分支散落全專案 = 每個平台都是驚喜箱。收攏到平台抽象層。

## Build 驗證（出了 build 不等於能玩）

自動化最後一哩：build 完自動做煙霧測試——

- [ ] 能啟動、進主選單
- [ ] 能進第一關並跑 60 秒不崩潰
- [ ] 版本號正確顯示
- [ ] （可自動化就自動化，不能就做成 5 分鐘人工清單）

## 常見陷阱

- **build 靠 IDE 按鈕**：按鈕後面的設定活在某人的編輯器裡，換機器就失傳。一切收進腳本與版控。
- **版本號手動改**：忘改的結果是三個不同的 build 都叫 0.9.2，回報的 bug 對不上版本。從 git 資訊自動生成。
- **CI 紅了當背景噪音**：紅燈三天沒人修，等於沒有 CI。紅燈 = 停止合入新東西。
- **只在發版前 build**：兩個月沒出過 build，發版週才發現建置壞了一個月——每日/每週 build 的意義就是把這種驚喜攤平。
