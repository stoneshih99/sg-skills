# 除錯的科學方法

除錯不是靈感，是**系統性收斂**。亂猜「大概是這裡吧」改一改的效率極低且會製造新 bug。這篇是把除錯當實驗做的流程與反模式。

## 核心迴圈

```
1. 可靠重現   ── 找到穩定觸發 bug 的最小步驟
2. 觀察       ── 收集事實（錯誤、log、狀態），不臆測
3. 假設       ── 提一個「為什麼會這樣」的具體、可否證的猜測
4. 預測       ── 若假設為真，改 X 應該會 Y
5. 一次測一個 ── 只改一個變數，驗證預測
6. 收斂或推翻 ── 對了就逼近 root cause；錯了就換假設（且復原剛才的改動）
```

每一輪都讓「可能的原因空間」縮小。關鍵是**每一步都基於事實與可否證的假設**，不是基於「感覺」。

## 先可靠重現，再動手

**重現不了的 bug 不能除**——你無從驗證任何修復。重現優先於一切：

- 找**最小、最穩定**的觸發步驟——砍掉無關步驟直到剩下必要條件（也順便逼近了 root cause）。
- 重現需要特定資料/時序/環境，就把那些固定下來（種子、固定輸入、鎖版本）。
- 只在生產偶發、本地重現不了 → 先加觀測性把重現條件撈出來（見 `observe-reading-signals.md`），別瞎修。
- **修好後要能「反向驗證」**：能一鍵讓 bug 重現、套上修復後消失——否則你不知道是真修好還是剛好沒踩到。

## root cause vs 症狀

**症狀是 bug 顯現的地方，root cause 是它產生的地方，兩者常不同**：

- `NullPointerException` 炸在第 500 行（症狀），但那個 null 是第 30 行就該被賦值卻沒有（root cause）。修第 500 行加個 null check，是把症狀壓下去，錯誤的狀態還在、會從別處再冒。
- 判準：問「為什麼」問到底（5 Whys）。修在「再問一個為什麼也答不出更深原因」的那層。
- **例外**：熱修上線止血時，先壓症狀是合理的權宜——但要留 ticket 追 root cause，別讓權宜變永久。

## 卡住時的解法

假設用光、還是找不到——通常是**某個「不可能」的假設其實是錯的**：

- **質疑假設**：你「確定沒問題」的那塊，真的驗證過嗎？把「我以為」逐一變成「我驗證過」。編譯的是這版嗎？跑的是這支嗎？改的檔存了嗎？
- **縮小到最小重現**：一路砍到不能再砍（見 `locate-narrowing-down.md`）——過程中原因往往自己浮出來。
- **講給別人/橡皮鴨聽**：逼自己把邏輯一步步說出口，講到某步會自己卡住——那就是漏洞。
- **退一步**：離開螢幕。連續盯著同一假設會產生隧道視野。
- **從能動的狀態往回逼**：找一個已知正常的版本/輸入，逐步逼近壞的，看哪一步翻轉（差異除錯）。

## 常見反模式

- **亂槍打鳥**：沒有假設就到處改、加 print，改到好了也不知道為什麼——每一改都要對應一個假設。
- **一次改多個東西**：好了不知是誰治的、壞了不知是誰弄的——一次一變數，其餘復原。
- **修症狀不修因**：加 null check／try-catch 吞掉——錯誤狀態還在，會再冒。
- **臆測代替觀察**：「一定是快取的問題」沒看證據就開修——先讀 log/stack trace 再假設。
- **不復原失敗的嘗試**：試錯改動堆疊，環境越弄越髒——假設被推翻就把改動還原。
- **沒重現就宣稱修好**：「應該是這個」改完 push——沒有反向驗證等於沒修。
