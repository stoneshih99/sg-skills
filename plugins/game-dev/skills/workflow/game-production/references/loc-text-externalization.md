# 字串外化

所有玩家可見的文字進字串表，程式與 UI 只拿 key。這是本地化的地基——地基歪了，後面每一種語言都在還債。

## 字串表結構

```
key                      | zh-TW        | en             | context（給譯者）
-------------------------|--------------|----------------|------------------
menu.start               | 開始遊戲      | Start Game     | 主選單按鈕
combat.damage_dealt      | 造成 {n} 傷害 | Dealt {n} damage | 戰鬥飄字
item.potion_hp.name      | 治療藥水      | Health Potion  | 道具名
item.potion_hp.desc      | 回復 {n} HP  | Restores {n} HP | 道具描述，n=數值
```

- **表是唯一真相**：進版控、有 schema 驗證（缺 key、缺翻譯、變數不對稱要在載入或 CI 時報錯——同 `../../../architecture/game-architecture/references/data-config-driven.md` 的載入即驗證）。
- **context 欄不是選配**：譯者看不到遊戲畫面，「Start」是開始遊戲還是發動引擎，靠 context 欄分辨（見 `loc-workflow.md`）。

## Key 設計

- **語意化階層**：`域.對象.欄位`（`item.potion_hp.name`）——不用 `text_047`，也不用英文原文當 key（原文一改 key 全斷）。
- **一處一 key**：同一個詞出現在按鈕與標題，是兩個 key——「OK」在不同 context 的譯法可能不同，共用 key 就綁死了。
- **廢 key 要清**：改版刪內容時同步清 key，或標記棄用——譯者最貴的浪費是翻沒人用的字串。

## 變數插值：本地化的第一地雷

- **具名佔位符**：`{player} 擊敗了 {enemy}`——**禁止**用順序佔位（`%s 擊敗了 %s`）或字串拼接：不同語言的語序不同，譯者必須能重排變數位置。

```
# 錯：拼接（語序被程式寫死）
text = get("prefix_dealt") + damage + get("suffix_damage")

# 對：模板插值（語序由譯文決定）
text = format(get("combat.damage_dealt"), n = damage)
```

- **複數規則**：「1 item / 2 items」在各語言的複數規則不同（有的語言 2-4 個一種形、5+ 另一種形）——用字串表的複數機制（per-key 多形），不要 `if n>1 加 s` 硬寫。
- **性別與敬語**（若有）：涉及角色性別變化的語言，模板要留分支欄位——第一天知道有這回事，需要時才接得上。

## 什麼要外化（清單）

- [ ] UI 全部文字（按鈕、標題、提示、錯誤訊息）
- [ ] 道具 / 技能 / 敵人的名稱與描述（通常直接掛在資料表旁邊，同一份 config 管理）
- [ ] 對話與劇情
- [ ] 圖片裡的字 → 改成圖 + 文字疊加（見 `art-asset-types.md` 的「文字不進圖」）
- [ ] 日期 / 數字 / 貨幣格式（用 locale 格式化函式，不要手拼）
- [ ] 平台商店文案、成就名稱（常被遺忘，release 期補很趕）

**不外化**：日誌與除錯文字（見 debug-toolkit——開發者看的東西保持單一語言，方便搜尋）。

## 常見陷阱

- **「先寫死，之後再抽」**：之後 = 幾千條散在程式裡的字串考古。第一條玩家可見文字就走表。
- **key 裡藏語言假設**：`msg_a_an_item` 這種為英文冠詞設計的 key 結構，其他語言用不上還得繞。
- **數字格式手拼**：`"$" + n` 在歐洲變笑話（貨幣符號位置、千分位、小數點都因地而異）。
- **富文本標記不統一**：顏色/粗體標記（`<color=red>`）散用且不進規範，譯者弄壞標記、QA 抓不完——標記語法進字串表規範，驗證腳本檢查標籤配對。
