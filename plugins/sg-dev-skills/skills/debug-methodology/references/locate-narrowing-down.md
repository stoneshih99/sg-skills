# 定位：把範圍砍到一半再一半

除錯大半時間花在「是哪裡壞的」。有效定位的共同數學是**二分搜尋**——每一步排除一半可能，`N` 個嫌疑犯 `log₂N` 步就逼到。這篇是四種定位手法與何時用哪個。

## 空間二分：在程式碼/資料裡切一半

當 bug 在「一大段流程/一大批資料」中，某處出錯：

- **切流程**：在中點觀察狀態（log 或中斷點）——狀態在中點還對嗎？對 → 壞在後半；錯 → 壞在前半。重複。
- **切輸入**：一大筆輸入觸發 bug，砍一半還觸發嗎？縮到「再砍就不觸發」的最小輸入（見下方最小重現）。
- **切程式碼**：註解掉/停用一半模組、feature flag、二分依賴——還壞嗎？

一個 1000 行的流程，10 次二分內定位到單行。**比從頭讀到尾快一個數量級**。

## 時間二分：git bisect

bug「以前沒有、現在有」——問題不在「哪裡」而在「哪個 commit 引入」：

- `git bisect` 在「已知好」與「已知壞」兩個 commit 間二分，每步 checkout 中點讓你測、標 good/bad，`log₂(commit 數)` 步定位到**引入 bug 的那個 commit**。
- 找到 commit＝拿到 diff＝原因範圍縮到那次改動（詳見 git-workflow 的 recovery/history 家族）。
- **可自動化**：`git bisect run <測試腳本>`——腳本回傳 0/非 0，git 自動跑完整個二分。
- 前提：要有一個**能判定 good/bad 的測試**（哪怕是手動一句判斷）。

## 最小重現（delta debugging）

把觸發 bug 的輸入/程式/設定，反覆砍到**再砍就不觸發**的最小集合：

- 每次移除一部分，仍觸發 → 那部分無關，丟掉；不觸發 → 那部分必要，留著。
- 收斂後剩下的就是**必要且充分**的觸發條件——原因通常一目了然。
- 副產品：最小重現是最好的 bug report、最快的回歸測試。

## 差異除錯：works here, not there

「在 A 環境/輸入正常，B 卻壞」——別直接鑽 B，**比對 A 與 B 的差異**：

- 列出兩者所有不同（版本、設定、資料、OS、權限、時序），逐一把 B 往 A 靠（或反之），看**哪一項翻轉結果**。
- 「我的機器上好的」＝一次差異除錯：差異藏在環境（依賴版本、環境變數、未提交的檔案、路徑大小寫）。
- 二分同樣適用：一次對齊一半的差異。

## 選型：先問 bug 的形狀

| bug 的樣子 | 先用 |
|-----------|------|
| 以前好、某次改動後壞 | **git bisect**（時間二分） |
| 一大段流程中途出錯 | **空間二分**（切流程/程式碼） |
| 特定輸入才觸發、輸入很大 | **最小重現**（砍輸入） |
| 這裡好那裡壞（環境/機器差異） | **差異除錯**（比對環境） |

實務上組合用：git bisect 找到壞 commit → 對 diff 做空間二分 → 縮最小重現寫成回歸測試。

## 常見坑

- **從頭讀到尾找 bug**：`O(N)` 硬讀——二分是 `O(log N)`，永遠先切一半。
- **git bisect 沒有判定準則**：good/bad 標錯整個結果作廢——先確定一個穩定的測法再 bisect。
- **bisect 踩到不相關的壞 commit**（編譯失敗等）：標 `git bisect skip`，別標 bad。
- **差異除錯只鑽壞的那邊**：忽略「好的那邊哪裡不同」——差異才是線索。
- **最小重現砍過頭**：把觸發條件也砍掉還以為修好了——每砍一刀都要確認仍觸發。
