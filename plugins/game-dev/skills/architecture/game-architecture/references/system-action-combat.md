# 動作戰鬥系統（Action Combat）

即時動作戰鬥的架構：狀態管理、命中判定、攻擊流程、傷害管線四層。核心難題是**時序**——動畫、判定、回饋、數值結算必須在正確的幀對齊，而且每一層都要能獨立擴充。

## 分層總覽

```
輸入/AI ──► 狀態管理（能不能出招）
              │
              ▼
          攻擊流程（何時出判定）──► 命中判定（打到誰）
                                        │
                                        ▼
                                   傷害管線（結算多少）──► 回饋事件（表現層）
```

各層只透過資料與事件溝通：判定層丟「命中事件」，管線層算數值，表現層收「結算事件」放特效——傷害公式不該知道 hitbox 形狀，特效不該知道暴擊率（分離原則見 `data-separation.md`）。

## 狀態管理：能力鎖用引用計數，不用 boolean

**問題**：`canMove = false` 誰設的？暈眩結束把它設回 true，但重攻擊後搖還沒完——boolean 被多個系統共寫，後設的蓋掉先設的，角色在該不能動時能動。

**解法**：每種能力一個**引用計數鎖**，各系統獨立加減：

```
struct AbilityLocks:
    moveLock = 0      # >0 即禁止移動
    attackLock = 0
    turnLock = 0

# 重攻擊後搖：moveLock += 1，後搖結束 -= 1
# 暈眩 debuff：onApply moveLock += 1，onRemove -= 1
# 兩者重疊時，先結束的只釋放自己那份，能力仍被鎖著——自然正確
```

- 加鎖/解鎖必須成對（作用域式 API 或綁定 buff 生命週期，見 `system-skill.md` 的 buff hooks）。
- 除錯時 log 每次加減鎖的來源（誰鎖的），配 watch 面板顯示當前鎖數（見 `../../../tools/game-tooling/references/debug-draw.md`）。

**狀態機的拆分**：單一狀態機（Idle/Run/Attack/Hit 全在一台）適合簡單角色；「移動 + 上身動作」要並行（邊跑邊射）就拆**雙層**——Locomotion 機與 Action 機各自運轉，用能力鎖協調（Action 進入重攻擊時鎖移動）。拆分準則：**兩類狀態會不會同時存在**；會，就拆。狀態機畫法見 `../../../diagram/game-diagrams/references/state-machine-diagram.md`。

## 命中判定：兩種實作模式

**盒型分工**先定清楚：

- **Hitbox（攻擊盒）**：攻擊者產生，定義「這一擊的作用範圍」，攜帶攻擊資料。
- **Hurtbox（受擊盒）**：掛在受擊者骨架上，定義「哪裡可以被打」，可分部位（頭部弱點倍率）。
- **互動盒**：拾取、對話等非戰鬥查詢，別跟戰鬥盒混用同一層。

**模式 A：常駐實例盒**——盒子作為元件掛在角色/武器上，由動畫事件開關：

- 優點：跟隨骨架自動變形（武器揮動軌跡真實）、可視化除錯直觀。
- 缺點：依賴動畫幀率（快速揮動會隔幀漏判，需掃掠補償）、盒子生命週期管理繁瑣。
- 適合：近戰為主、攻擊軌跡重要的動作遊戲。

**模式 B：即時查詢**——在指定幀執行一次形狀查詢（overlap/sweep），參數全在資料：

```
# 攻擊資料表的一列（config-driven，見 data-config-driven.md）
attack_id: heavy_slash
    active_frames: [12, 16]        # 第 12-16 幀出判定
    shape: box(2.0, 1.5, 1.2)      # 尺寸
    offset: forward 1.5             # 相對攻擊者
    hit_once_per_target: true
```

- 優點：資料驅動（改判定不改場景物件）、無實例管理、天然支援一擊一查。
- 缺點：形狀不跟骨架連續變形（用多幀多次查詢近似）。
- 適合：判定規則多、需要大量調參與批次平衡的專案。

**選擇**：不確定就選 B——資料驅動的調參效率在平衡期回本；A 留給「揮擊軌跡本身是玩法」的遊戲。兩種模式都要做**除錯繪製**（判定形狀 + 命中點，見 game-tooling 的 debug-draw）。

**同一揮擊防重複命中**：每次攻擊生成 `swing_id`，命中登記表記 `(swing_id, target)`，重複跳過。多段攻擊 = 多個 swing_id。這張表同時解決「一刀穿過三個 hurtbox 只算一次」。

**過濾與剪枝**：先做便宜檢查再做形狀檢查——陣營過濾（碰撞層）、距離平方粗篩、無敵/死亡 tag 剔除（容器選型見 `algo-data-structures.md` 的空間分割）。

## 攻擊流程：判定窗口從哪來

攻擊的時間軸有兩個驅動來源，擇一為主：

- **動畫事件驅動**：動畫片段內嵌事件（第 N 幀開判定、第 M 幀關）。直觀、動畫師可調；缺點是邏輯藏在動畫資產裡，批次檢視困難、換動畫要重埋。
- **資料時間軸驅動**：攻擊資料表定義時間軸（前搖 X 幀 → 判定 [a,b] → 後搖、取消窗口 [c,d]），動畫只負責跟播。邏輯集中可查、可脫離動畫測試（headless 平衡模擬）；動畫與資料的幀數要有校驗工具防止漂移。

**建議**：資料時間軸為主、動畫跟隨——與 `../../../planning/game-design/references/feel-input-responsiveness.md` 的「動畫服務手感」同一結論，且時間軸資料就是取消窗口與輸入緩衝的判定依據。

**遠程與投射物**：投射物是獨立場景物件（自帶移動、碰撞、生命週期，用物件池），攜帶一份攻擊資料快照——發射後攻擊者的屬性變化不回溯影響已飛出的子彈（快照原則，避免「射出後換武器傷害變了」的靈異）。高速投射物用 raycast/掃掠防穿隧（見 `algo-physics.md`）。

## 傷害管線：階段化的純函數

命中事件進入管線，**分階段結算，每階段只做一件事**：

```
DamagePacket（純資料）: source, target, base, tags[physical, heavy], swing_id

pipeline:
    1. gather      攻擊方修飾（力量加成、buff 的 +15% 重擊傷害）
    2. pre_mitigate 命中判態（暴擊判定、格擋判定——順序在此寫死）
    3. mitigate    防禦方減免（護甲、抗性、傷害減免 buff）
    4. clamp       上下限（最低 1 點、斬殺閾值）
    5. apply       扣血、破霸體——唯一改狀態的階段
    6. emit        發結算事件（傷害數字、hitstop、音效、擊退）
```

- **修飾器都掛在階段上**：buff「+20% 對燃燒目標傷害」= 註冊在 gather 階段、條件 target has burning tag 的修飾器（buff 系統見 `system-skill.md`）。加新機制 = 加修飾器，不改管線本體。
- **順序顯式化**：暴擊先算還是格擋先判？護甲先減還是百分比減免先扣？——這些順序寫在管線定義裡，全遊戲一致。散落各處的 if 是平衡災難的溫床。
- **1-5 是純計算**（吃 packet 吐 packet），只有 apply 改世界狀態——可單元測試、可 headless 模擬平衡、可回放（純資料的紅利，見 `data-separation.md`）。
- **emit 的事件與回饋同幀**：hitstop、閃白、音效在收到結算事件的同一幀觸發（回饋層見 `../../../planning/game-design/references/feel-impact-feedback.md`）。

## 受擊方：霸體與無敵要資料化

- **受擊反應分級**：輕（僅閃白）/ 中（硬直踉蹌）/ 重（擊飛倒地），由攻擊資料的 `hit_level` 對照受擊方的**霸體值（poise）**決定——兩邊都是資料，平衡在表裡調。
- **無敵窗口**：翻滾 i-frame、受擊後短暫無敵——實作為帶時效的 tag（buff 的一種），判定層的剪枝統一讀 tag，不要每個系統自己記 boolean（又回到引用計數的教訓）。

## 常見陷阱

- **能力控制用 boolean**：本篇第一節的問題，最常見也最貴。
- **傷害計算散落**：武器腳本算一點、buff 腳本改一點、最後沒人知道一刀 137 是怎麼來的——管線化 + 每階段可 log（傷害屍檢見 game-tooling 的 debug-logging）。
- **判定跟渲染幀率走**：高刷新率機器判定窗口變短——判定走固定步長邏輯幀，渲染只負責插值顯示。
- **投射物讀活體屬性**：發射後屬性即時查詢源頭，快照原則被破壞。
- **回饋在判定層觸發**：hitbox 重疊就播特效，結果被格擋的攻擊也噴血——回饋只聽 emit 階段的結算事件。
